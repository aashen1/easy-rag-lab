# 版本节奏：如何避免发版阻塞与功能堆积

<!-- status: active -->

> 创建日期：2026-04-28
> 来源：v0.1.8→v0.1.13 的复盘教训

---

## 一、发生了什么

v0.1.8 发布后，v0.1.9 的目标定为"评测链路修复"。但这条链路因前期快速开发积累了大量技术债——bug、补丁、逻辑不通顺——导致评测结果虚高或报错，修了又修，始终无法达到"可信"的标准。

在修评测的过程中，其他工作并行推进：多 parser 框架、Artifact 体系、Golden 测试集、Issue 系统、Streamlit UI……这些功能各自独立开发，却因为 v0.1.9 的发版目标被阻塞，无法正式发布。最终 v0.1.8 到 HEAD 之间堆积了 **507 个 commit**，是之前每个版本（57-62 commit）的 **8 倍**。

事后回看，这 507 个 commit 被重新梳理为 5 个版本（v0.1.9~v0.1.13），每个都有清晰的主题和交付。但这个过程是事后补的，不是事前规划的。

---

## 二、根本原因

### 2.1 版本目标耦合了"修复"与"发布"

v0.1.9 的目标是一个**修复型任务**（让评测链路可信），但修复型任务天然具有**不确定的工期**——你不知道地下埋了多少雷。把发版绑定在一个不确定工期的任务上，就等于把整个项目的发布节奏交给了运气。

### 2.2 "做完再发"的执念

"这个版本的目标还没完成，不能发版"——这个想法看似合理，实则危险。它假设了：

1. 版本目标是可以精确预估的（实际上不行，尤其是修复型任务）
2. 其他完成的工作不值得独立发布（实际上值得）
3. 推迟发布不会造成额外成本（实际上会：验收困难、文档混乱、上下文丢失）

### 2.3 平行开发缺乏版本归属

在修评测的同时，其他功能在平行推进，但没有人为它们分配版本号。结果是：

- 完成的功能没有验收就堆在 dev 分支上
- 文档系统无法追踪这些功能属于哪个版本
- 下一个 AI session 看到的是一堆无组织的变更，而不是有叙事的版本

## 三、原则：版本节奏的五个法则

### 法则一：版本绑定时间，不绑定任务

> 版本号是时间戳，不是任务清单的完成证书。

**做法**：设定发版周期（如每周一个 minor 版本），到时间就发。没做完的任务移到下个版本，不阻塞发版。

**反例**：v0.1.9 定为"评测链路修复"，结果评测链路修了 8 天还没修好，其他 400+ commit 跟着等。

**正例**：v0.1.9 应该在 4 月 21 日左右发版，主题定为"RAGAS 集成与评测增强"。评测链路的 bug 继续修，但不阻塞发版。修好了就是 v0.1.10 的内容。

### 法则二：一个版本讲一个故事

> 每个版本应该有一个清晰的叙事，让人一眼看出"这一版为什么存在"。

**做法**：版本主题不是功能列表，而是一句话回答"这一版让用户/开发者获得了什么"。

| 好的主题 | 坏的主题 |
|---------|---------|
| 评测双引擎 | 评测链路修复 + RAGAS 集成 + Recall@k + ruff 配置 |
| 解析新纪元 | 多 parser + page-aware + Artifact 迁移 + tokenizer 统一 |
| 链路统一 | Golden 收编 + adversarial + 数值校验 + excerpt 验证 + BUG-026/027/029/030/031 |

好的主题让人记住版本；坏的主题让人淹没在细节里。

### 法则三：修复型任务不占版本主题

> 修 bug 是卫生工作，不是版本灵魂。

**做法**：

- **小型修复**：归入当前版本的"附带修复"，不占主题
- **大型修复**（如"评测链路全面可信"）：拆成多个独立的小修复，每个修复完成后立即合入，不单独占一个版本主题
- **系统性重构**：如果修复涉及架构调整，按功能型任务规划版本，修复是手段不是目的

**反例**：v0.1.9 的主题是"统一测试集生成链路"——这本质上是一个修复+重构任务，工期不确定，阻塞了整个发版。

**正例**：如果评测链路有问题，版本主题应该是"评测双引擎"（正向目标：我们有了两种评测方式），而不是"评测链路修复"（负向目标：修好了之前坏的东西）。

### 法则四：完成即归档，不等版本

> 完成的功能应该立即获得版本归属，而不是等到"版本目标完成"才一起打包。

**做法**：

1. 每完成一个功能域（如 multi-parser 框架），立即在 version-history.md 中记录
2. 如果当前版本已经积累了一定量的变更（建议阈值：**50-80 commit**），就该考虑发版
3. 发版时回顾这段时间的变更，按叙事逻辑整理版本主题

**反例**：507 个 commit 堆了 8 天，事后才梳理出 5 个版本。

**正例**：每 50-80 commit 发一个版本，每个版本有清晰的 git tag 和验收报告。

### 法则五：发版是检查点，不是终点线

> 发版的意义不是"做完了"，而是"到这里了，我们检查一下"。

**做法**：

- 发版时做轻量验收：跑测试、检查 lint、确认文档一致性
- 不要求所有功能都"打磨完毕"才能发版
- 未打磨的功能在版本记录中标注"初版"或"实验性"，下个版本继续迭代

**反例**：因为评测链路"还不够好"就不发版，导致其他已完成的、可用的功能也无法交付。

**正例**：v0.1.9 发版时 RAGAS 集成已可用但还有已知问题，在版本记录中标注"RAGAS 基本链路已通，已知问题见 backlog"，后续版本继续修复。

## 四、实操指南

### 4.1 版本规划节奏

```
每周一个 minor 版本（v0.1.X）
    │
    ├── 周初：确定本周版本主题（一句话）
    ├── 周中：开发 + 持续提交
    ├── 周末：回顾变更，整理版本叙事，打 tag，发版
    └── 发版后：轻量验收 + 更新文档
```

### 4.2 版本主题选择

优先级从高到低：

1. **正向目标**（"我们获得了 X"）优于负向目标（"我们修好了 Y"）
2. **用户可感知**的变更优于内部重构
3. **独立完整**的功能域优于零散的补丁集合

### 4.3 Commit 阈值预警

| 累计 commit 数（自上个 tag 起） | 建议动作 |
|------|------|
| 0-30 | 正常开发 |
| 30-50 | 开始考虑版本主题 |
| 50-80 | 应该发版了 |
| 80-120 | ⚠️ 发版严重滞后，立即规划发版 |
| 120+ | 🔴 紧急：版本已失控，参考本文档的教训 |

### 4.4 修复型任务的版本归属

```
修复型任务
├── 小型修复（1-3 commit）
│   └── 归入当前版本的"附带修复"
├── 中型修复（4-10 commit）
│   └── 如果与当前版本主题相关 → 归入当前版本
│   └── 如果无关 → 独立提交，下个版本收录
└── 大型修复（10+ commit）
    └── 拆分为多个独立修复，按上述规则分别处理
    └── 如果无法拆分 → 重新审视是否应该作为独立版本
```

### 4.5 平行开发的版本归属

当多个功能域平行开发时：

1. 每个功能域在自己的分支上开发
2. 合入 dev 时，在 commit message 中标注功能域
3. 发版时，按功能域整理版本叙事
4. 如果某个功能域已完成但当前版本主题不匹配，可以：
   - 方案 A：调整版本主题以包含该功能域
   - 方案 B：该功能域等下个版本发布
   - 方案 C：拆分为两个版本（推荐）

## 五、AI 协作规范

### 5.1 AI 在版本管理中的职责

1. **监控 commit 数量**：每次对话开始时，检查自上个 tag 以来的 commit 数量，超过 50 时主动提醒
2. **维护版本叙事**：每次完成一个功能域后，在 version-history.md 中添加草稿记录
3. **发版提醒**：当 commit 数量超过阈值时，建议用户发版
4. **版本主题建议**：根据近期变更，提出版本主题建议

### 5.2 AI 不应该做的事

1. **不应该阻塞发版**：不要因为"某个功能还没打磨好"就建议推迟发版
2. **不应该批量堆积变更**：不要在一个版本目标下堆积数百个 commit
3. **不应该事后补版本**：版本应该在 commit 发生时规划，不是事后梳理

## 六、检查清单

### 发版前

- [ ] 自上个 tag 以来的 commit 数量是否在 50-80 范围内？
- [ ] 版本主题是否是一句话的正向目标？
- [ ] version-history.md 是否已更新？
- [ ] CLAUDE.md 当前状态是否已更新？
- [ ] git tag 是否已打？
- [ ] 测试是否通过？
- [ ] lint 是否通过？

### 每次对话开始时

- [ ] 自上个 tag 以来的 commit 数量是多少？是否超过阈值？
- [ ] 是否有完成的功能域尚未记录到 version-history.md？
- [ ] 当前版本主题是否仍然合理？是否需要调整？

1. **507 个 commit 堆在 8 天里**——这是真实发生过的教训
2. 版本号是时间戳，不是任务清单的完成证书
3. 发版是检查点，不是终点线
4. 修 bug 是卫生工作，不是版本灵魂
