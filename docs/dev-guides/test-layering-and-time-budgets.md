# 测试分层与 CI/CD 耗时预算

> 最后更新: 2026-04-26

本文档介绍软件工程中关于测试分层与自动化流水线耗时预算的业界共识，以及在本项目中的落地策略。

---

## 1. 核心原则：每个阶段只跑该跑的测试

测试不是越多越好，而是**在对的时机跑对的测试**。一条简单的规则：

> **开发者等待时间与测试覆盖深度成反比——越频繁触发的阶段，测试应该越轻量。**

原因很直观：如果 commit 前的检查要等 30 秒，开发者就会习惯性 `--no-verify` 跳过，防线形同虚设。反之，如果只在夜间跑全量测试，合并到主分支的坏代码可能要几小时后才被发现，回滚成本很高。

所以关键不是"让测试变快"，而是"让每个阶段只承担它该承担的检查深度"。

---

## 2. 四层模型

按触发时机从频繁到稀疏，业界普遍采用四层测试分层：

```
频次   阶段              耗时预算        检查深度
─────────────────────────────────────────────────────
高频   Commit 级         < 10 秒        格式 + 纯逻辑
中频   Push / PR 级      1 ~ 5 分钟     单元 + 轻量集成
低频   Merge / CI 级     5 ~ 15 分钟    全量测试
极低频  Nightly 级        无硬限制       性能 / 压力 / 安全
```

### 2.1 Commit 级（pre-commit）

| 维度 | 说明 |
|------|------|
| **触发时机** | `git commit` 前 |
| **耗时预算** | **< 10 秒**，理想 **< 5 秒** |
| **跑什么** | Lint + Format + 纯单元测试（无 IO、无网络、无数据库） |
| **核心原则** | 开发者不能感受到"等待"，否则会跳过 |
| **典型内容** | 代码风格检查、参数校验、数据转换、序列化/反序列化、纯逻辑计算 |
| **排除什么** | 文件读写、网络请求、数据库、重计算 fixture、需要真实环境的测试 |

> **经验法则**：Google 内部实践要求 commit 级检查控制在 **5 秒以内**。超过 10 秒，开发者就会开始用 `--no-verify` 绕过。

### 2.2 Push / PR 级（pre-push 或 CI 快速门控）

| 维度 | 说明 |
|------|------|
| **触发时机** | `git push` 前，或 CI 中 PR 的快速检查阶段 |
| **耗时预算** | **1 ~ 5 分钟** |
| **跑什么** | 单元测试 + 轻量集成测试（本地 IO、内存数据库、mock 服务） |
| **核心原则** | 推代码前确认"我的改动没破坏已有功能" |
| **典型内容** | Commit 级全部 + 文件解析测试、索引构建测试、Pipeline 串联测试（mock 外部 API） |
| **排除什么** | 真实外部 API 调用、长时间运行的评估测试、端到端流程 |

### 2.3 Merge / CI 级（post-merge 或 CI 完整阶段）

| 维度 | 说明 |
|------|------|
| **触发时机** | 合入主分支后，或 CI 的完整测试阶段 |
| **耗时预算** | **5 ~ 15 分钟**（可接受），**> 30 分钟**（需要优化） |
| **跑什么** | 全量测试，包括集成测试和端到端测试 |
| **核心原则** | 确保整体系统完整性，合入主分支的代码不会破坏全局 |
| **典型内容** | Push 级全部 + 真实 API 调用、数据库集成、跨模块端到端 |
| **优化手段** | 并行化（多 runner / pytest-xdist）、增量测试（只跑受影响模块） |

### 2.4 Nightly 级（定时任务）

| 维度 | 说明 |
|------|------|
| **触发时机** | 每天夜间或定期执行 |
| **耗时预算** | **无硬限制**，通常 30 分钟 ~ 数小时 |
| **跑什么** | 性能测试、压力测试、全量回归、安全扫描、评估基准 |
| **核心原则** | 不阻塞日常开发，但能发现慢退化 |

## 3. 业界实践参考

| 公司/项目 | Commit 级 | PR 级 | Merge/CI 级 |
|-----------|-----------|-------|-------------|
| Google | < 5s（只跑受影响测试） | ~2-5 min | ~10-15 min（大规模并行） |
| Meta | < 10s | ~3 min | ~10 min |
| GitHub | lint + typecheck ~3s | ~5 min | ~15 min |
| 典型 Python 项目 | ruff + 纯单元 ~5s | pytest -m "not slow" ~2min | 全量 pytest ~10min |

## 4. 为什么是这些数字？

耗时预算不是拍脑袋定的，背后有认知科学和工程实践的支撑：

### 4.1 10 秒法则

人对于"即时反馈"的忍耐阈值大约是 **10 秒**。超过 10 秒，注意力就会转移（切到浏览器、看手机），回来后需要重新进入上下文——这个"重新进入"的成本远比等 10 秒本身高。

这就是为什么 commit 级必须 < 10 秒：它不是在省时间，而是在**保护开发者的心流状态**。

### 4.2 5 分钟法则

5 分钟是人能"保持等待"而不切换任务的上限。超过 5 分钟，开发者会去做别的事，等回来时可能已经忘了刚才在做什么。PR 级测试控制在这个范围内，是为了让开发者能"推完代码等一下就能看到结果"。

### 4.3 15 分钟法则

15 分钟是"喝杯咖啡回来刚好看到结果"的时间。CI 级测试在这个范围内，开发者可以在合并后去做别的事，回来确认结果。超过 30 分钟就需要考虑拆分或并行化。

## 5. 测试分类的技术手段

### 5.1 pytest marker 分层

最常见的方式是用 pytest marker 给测试打标签：

```python
# pyproject.toml
[tool.pytest.ini_options]
markers = [
    "integration: marks tests that call external APIs",
    "slow: marks tests that take > 1s (IO, file parsing, etc.)",
]
```

然后在测试中使用：

```python
@pytest.mark.slow
def test_parse_large_pdf():
    ...

@pytest.mark.integration
def test_query_real_llm():
    ...
```

不同阶段选择不同 marker 组合：

```bash
# Commit 级：只跑纯单元测试
pytest tests/ -m "not integration and not slow"

# Push/PR 级：跑单元 + 轻量集成
pytest tests/ -m "not integration"

# Merge/CI 级：全量
pytest tests/
```

### 5.2 耗时自动分类

手动标记 marker 容易遗漏。更可靠的方式是**根据实际耗时自动分类**：

```bash
# 先跑一遍，输出每个测试的耗时
pytest tests/ --durations=0 -q

# 找出 > 1s 的测试，给它们加 @pytest.mark.slow
```

也可以用 pytest 的 `--durations-min` 参数设置阈值，只显示超过指定时间的测试。

### 5.3 并行化加速

对于已经分好层的测试，还可以通过并行化进一步压缩耗时：

```bash
# pytest-xdist：多进程并行
pytest tests/ -n auto

# pytest-xdist + 分层组合
pytest tests/ -m "not integration" -n auto
```

并行化通常能带来 **2-4x** 的提速（取决于 CPU 核数和测试的 IO 密度）。

## 6. 本项目现状与改进方向

### 6.1 现状

| 阶段 | 实际内容 | 耗时 | 评价 |
|------|---------|------|------|
| pre-commit | ruff lint + format + 通用检查 | ~3-5s | ✅ 合理 |
| post-merge | 全量 1338 个单元测试 | ~30s | ⚠️ 阶段正确但缺少中间层 |

当前缺少 **commit 级的快速测试层** 和 **push/PR 级的中等测试层**。

### 6.2 改进路线

```
现状                              目标
──────────────────────────────────────────────────────────
pre-commit: lint/format           pre-commit: lint/format + 纯单元测试 (< 10s)
                                  pre-push:   单元 + 轻量集成 (< 3min)
post-merge: 全量测试 (~30s)       post-merge: 全量测试 + xdist 并行 (~10s)
```

具体步骤：

1. **添加 `slow` marker**：给耗时 > 1s 的测试标记 `@pytest.mark.slow`
2. **新增 `test-fast` 任务**：`pytest tests/ -m "not integration and not slow"`
3. **pre-commit 加入快速测试**：`entry: pixi run test-fast`
4. **post-merge 加 xdist 并行**：`pytest tests/ -m "not integration" -n auto`

## 7. 常见误区

### 误区 1："测试越快越好"

速度不是目的，**正确的分层**才是。一个 0.1 秒但不测关键逻辑的测试，不如一个 2 秒但覆盖核心路径的测试。关键是在对的阶段跑对的测试。

### 误区 2："commit 级也要跑全量测试"

全量测试放在 commit 级只会导致两个结果：开发者跳过钩子，或者开发者减少 commit 频率（攒一堆改动再提交）。两者都比"commit 级只跑快速测试"更糟。

### 误区 3："post-merge 测试失败就要立即修"

post-merge 测试是**非阻塞**的——merge 已经完成了。它的作用是**通知**你合并可能出了问题，你可以选择回滚（`git reset --hard ORIG_HEAD`）或继续修复。不需要像 pre-commit 那样"不通过就不让过"。

### 误区 4："并行化可以解决一切"

并行化能压缩耗时，但不能替代分层。如果 1338 个测试全放在 commit 级并行跑，即使从 30 秒降到 10 秒，对于 commit 这个动作来说仍然太重。分层是根本，并行化是锦上添花。
