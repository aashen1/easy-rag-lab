# 活文档规范：跨 Session 功能追踪方法论

<!-- status: active -->

> 最后更新: 2026-05-10
> 级别: 强制规范（所有新功能 spec 必须遵循）

---

## 一、问题背景

### 1.1 编号快照范式的致命缺陷

项目早期采用"编号快照"范式管理功能 spec：每个 session 产出一组新文档，按递增编号放入子目录：

```
.trae/specs/maintenance-agent/
├── 0-initial-plans/
├── 1-add-maintenance-agent/
├── 2-round1-check-and-report/    # "T5: 0%, T8: 0%"
├── 3-small-bugfix-and-cleaning/
├── 4-maintenance-agent-phase2/
├── 5-round3-check-and-phase3-impl/  # 又抄 "T5: 0%, T8: 0%"
├── 6-all-done-check-and-fix/
├── 7-fix-remaining-issues/
├── 8-many-bugfix/                 # 实际把 T5、T8 做完了
└── 9-check-result/                # 前半 "0%"，后半 "已完成"
```

这种范式在"给人类按时间翻阅"时很自然，但在"给 AI 读取当前状态"时有三个致命问题：

| 问题 | 严重度 | 具体表现 |
|------|--------|---------|
| **信息过时误导** | 🔴 致命 | AI 读到旧快照中的"未完成"就信了，不会继续往后读 |
| **文档内部矛盾** | 🔴 致命 | 同一份报告前半说"0%"后半说"已完成"，AI 不知该信哪个 |
| **上下文浪费** | 🟡 中等 | AI 要读 10 个文件夹才能拼出当前状态，token 消耗大 |

### 1.2 根本原因

编号快照范式本质上是**用文件系统模拟 Git commit**——每个文件夹是一个不可变快照，但没有 rebase 机制修正历史中的错误判断。AI 在顺序读取时，会把过时信息当作当前状态。

## 二、活文档范式

### 2.1 核心原则

> **AI 读到的第一眼必须是当前状态，而不是历史快照。**

活文档范式的核心是：每个功能目录下维护**一套持续更新的文档**，而非多组编号快照。文档内部分为两个区域：

- **当前状态区域**：覆盖写，永远反映最新情况
- **变更日志区域**：只追加，保留审计轨迹

### 2.2 目录结构

```
.trae/specs/<feature-name>/
├── spec.md        # 功能规范（活文档）
├── progress.md    # 进度追踪（活文档）
├── handoff.md     # 交接文档（活文档）
└── checklist.md   # 验收清单（活文档）
```

**禁止**在功能目录下创建编号子目录（`0-xxx/`、`1-xxx/` 等）。

### 2.3 与编号快照范式的对比

| 场景 | 编号快照范式 | 活文档范式 |
|------|-------------|-----------|
| AI 读到"T5: 0%" | 在 5 号文件夹，8 号才做完，AI 可能没读到 | progress.md 直接写"T5: 100%"，AI 第一眼就看到 |
| 需要回溯决策原因 | 翻遍 0-9 号文件夹找线索 | spec.md 的 Decision Log 一目了然 |
| 验收报告前后矛盾 | 9 号文件夹前半"0%"后半"已完成" | 不可能发生，progress.md 只有一个当前值 |
| Token 消耗 | AI 读 10 个文件夹 | AI 读 4 个文件 |
| 历史审计 | 靠文件夹编号 | 靠 Git diff + 文档内 Changelog |

## 三、四件套文档规范

### 3.1 spec.md — 功能规范

**职责**：定义功能的需求、范围和设计决策。

**写入时机**：功能启动时创建，需求变更时更新。

**结构模板**：

```markdown
# <功能名称> 功能规范

## 当前需求

### 核心能力
| ID | 能力 | 优先级 | 状态 |
|----|------|--------|------|
| C1 | xxx | P0 | ✅ |
| C2 | xxx | P1 | ⏸️ 暂缓 |

### 范围定义
- 包含：xxx
- 不包含：xxx

## Decision Log
| 日期 | 决策 | 原因 | 替代方案 |
|------|------|------|---------|
| 2026-05-05 | T5 标记暂缓 | 设计不清晰 | — |
| 2026-05-08 | T5 改为 prompt 指导 | 用户建议简化 | 显式切换机制 |
```

**关键规则**：
- "当前需求"区域覆盖写——过时的需求直接删掉或标 🗑️，不要留旧版本
- "Decision Log"只追加——记录每个决策的日期、内容、原因和被否决的替代方案
- AI 读取时，"当前需求"是权威信息，Decision Log 仅供参考

### 3.2 progress.md — 进度追踪

**职责**：追踪功能各任务的完成度和变更历史。

**写入时机**：每次 session 结束前必须更新。

**结构模板**：

```markdown
# <功能名称> 进度追踪

## 当前状态

| Task | 内容 | 完成度 | 最后更新 |
|------|------|--------|---------|
| T1 | SqliteSaver 持久化 | 100% | 2026-05-06 |
| T5 | 轻量/全量双模式 | 100% | 2026-05-08 |
| T8 | Phase C 迁移 | 100% | 2026-05-09 |

## 遗留问题

| 问题 | 优先级 | 状态 |
|------|--------|------|
| Streamlit interrupt 缺少自动化测试 | P2 | 待做 |

## Changelog

| 日期 | 变更 | 原因 |
|------|------|------|
| 2026-05-05 | T5: 0% → 暂缓 | 验收时未实现 |
| 2026-05-08 | T5: 暂缓 → 100% | 改为 prompt 指导实现 |
| 2026-05-05 | T8: 0% | 验收时未实现 |
| 2026-05-09 | T8: 0% → 100% | 按 dual-path-cleanup 计划完成 |
```

**关键规则**：
- "当前状态"表格覆盖写——完成度永远是最新值，不保留历史值
- "遗留问题"持续维护——解决了就删掉，新发现的追加
- "Changelog"只追加——记录每次完成度变更的日期、旧值→新值、原因
- **AI 读取时，"当前状态"是权威信息，Changelog 仅供参考**

### 3.3 handoff.md — 交接文档

**职责**：记录 session 间的工作交接信息。

**写入时机**：每次 session 结束前覆写。

**结构模板**：

```markdown
# <功能名称> 交接

## 上次 Session 做了什么
（简要描述，3-5 条）

## 下次 Session 应该做什么
（按优先级排列，3-5 条）

## 遗留风险
（如有）
```

**关键规则**：
- **每次 session 开始时覆写**——只保留最近一次交接信息
- 这是 session 间的"接力棒"，不需要历史记录
- 如需追溯历史，用 `git log -- handoff.md`

### 3.4 checklist.md — 验收清单

**职责**：定义验收标准和验收结果。

**写入时机**：功能启动时创建验收项，验收通过时更新结果。

**结构模板**：

```markdown
# <功能名称> 验收清单

## 验收项

- [x] C1: LangGraph 编排框架 ✅ (2026-05-03)
- [x] C6: 轻量/全量双模式 ✅ (2026-05-08, 通过 prompt 指导实现)
- [x] T8: Phase C 迁移 ✅ (2026-05-09, 全部迁移完成)
- [ ] Streamlit interrupt 自动化测试

## 验收历史

| 日期 | 验收范围 | 结果 | 备注 |
|------|---------|------|------|
| 2026-05-05 | Phase 3 验收 | T5/T8 未通过 | 设计不清晰 |
| 2026-05-09 | 修复后验收 | 全部通过 | — |
```

**关键规则**：
- 验收项打钩后追加日期和简要说明
- "验收历史"只追加
- 未通过的验收项保留在"验收项"中不打钩，在"验收历史"中记录原因

## 四、AI 读取规则

### 4.1 读取顺序

AI 在接手一个功能时，**必须按以下顺序读取**：

1. **progress.md 的"当前状态"区域** — 第一眼看到的就是最新完成度
2. **spec.md 的"当前需求"区域** — 了解功能范围
3. **checklist.md 的"验收项"区域** — 了解哪些已验收、哪些未验收
4. **handoff.md** — 了解上次 session 做了什么、下次应该做什么

**禁止**先读 Changelog/Decision Log 再读当前状态——历史信息会误导 AI 对当前状态的判断。

### 4.2 读取时的权威性层级

| 区域 | 权威性 | 说明 |
|------|--------|------|
| progress.md "当前状态" | 🔴 最高 | 这是当前进度的唯一真相源 |
| spec.md "当前需求" | 🔴 最高 | 这是当前需求的唯一真相源 |
| checklist.md "验收项" | 🟡 高 | 验收结果以代码实际状态为准 |
| handoff.md | 🟡 高 | 交接信息以最新 session 为准 |
| Changelog / Decision Log | 🟢 参考 | 仅用于理解"为什么变成这样"，不用于判断"现在是什么状态" |

### 4.3 禁止的行为

| 禁止行为 | 原因 |
|---------|------|
| 在功能目录下创建编号子目录 | 回到快照范式，导致信息过时 |
| 在 Changelog 中修改历史记录 | Changelog 是只追加的审计日志 |
| 从旧文档中引用过时的完成度 | 必须以 progress.md 当前状态为准 |
| 创建新的验收报告而不更新 checklist.md | 验收结果必须反映在 checklist 中 |
| 保留多份 spec/progress/checklist | 一套功能只有一套活文档 |

## 五、Session 工作流

### 5.1 Session 开始时

```
1. 读取 progress.md "当前状态" → 了解功能完成度
2. 读取 spec.md "当前需求" → 了解功能范围
3. 读取 checklist.md "验收项" → 了解验收状态
4. 读取 handoff.md → 了解上次交接信息
5. 对照代码验证 progress.md 中的完成度是否准确
   - 如发现过时信息，立即更新 progress.md
```

### 5.2 Session 工作中

```
1. 完成一个任务 → 更新 progress.md "当前状态" + 追加 Changelog
2. 需求变更 → 更新 spec.md "当前需求" + 追加 Decision Log
3. 验收通过 → 更新 checklist.md "验收项"
4. 每个逻辑工作单元 → commit + 文档更新（原子操作）
```

### 5.3 Session 结束时

```
1. 更新 progress.md → 确保当前状态准确
2. 覆写 handoff.md → 记录本次做了什么、下次应该做什么
3. 更新 checklist.md → 标记新通过的验收项
4. Commit 所有文档变更
```

## 六、与现有体系的关系

### 6.1 与抛接球年轮的关系

活文档规范是抛接球年轮方法论在**功能级别**的补充：

| 层级 | 方法论 | 文档载体 |
|------|--------|---------|
| 版本级别 | 抛接球年轮 | `docs/version-history.md` + `docs/reviews/vX.X.X/` |
| 功能级别 | 活文档规范 | `.trae/specs/<feature>/` 四件套 |

版本发版后，功能目录整体归档到 `docs/.archive/`，与现有归档机制无缝衔接。

### 6.2 与 Issue 系统的关系

| 维度 | Issue 系统 | 活文档 |
|------|-----------|--------|
| 粒度 | 单个 bug/feature | 整个功能模块 |
| 生命周期 | 短（创建→完成） | 长（功能启动→归档） |
| 交互方式 | CLI 命令 | 直接编辑 md |
| 用途 | 项目级待办追踪 | 功能级需求与进度追踪 |

功能开发中发现的 bug 应创建 Issue，同时在 progress.md 的"遗留问题"中引用 Issue ID。

### 6.3 与 project-memory skill 的关系

project-memory skill 的"新 session 启动检查清单"中，Tier 3 深入读取步骤应增加：

> 当工作涉及特定功能时，读取 `.trae/specs/<feature>/progress.md` 的"当前状态"区域。

## 七、迁移指南

### 7.1 从编号快照迁移到活文档

对于已有的编号快照目录（如 `maintenance-agent/0-xxx/` 到 `9-xxx/`）：

1. **创建四件套**：在功能目录下新建 `spec.md`、`progress.md`、`handoff.md`、`checklist.md`
2. **提取当前状态**：从最新编号文件夹和代码实际状态中，提取当前完成度写入 progress.md
3. **提取决策历史**：从所有编号文件夹中，提取关键决策写入 spec.md 的 Decision Log
4. **提取验收结果**：从最新验收报告中，提取验收项写入 checklist.md
5. **归档旧文件夹**：将编号子目录整体移入 `docs/.archive/`

### 7.2 迁移时的注意事项

- 迁移前先 commit，确保 Git 历史完整
- progress.md 的"当前状态"必须与代码实际状态一致，不与旧文档中的过时判断一致
- Decision Log 只记录关键决策，不要把所有文档内容都搬过来

---

## 八、自检清单

在创建或更新活文档时，用以下清单自检：

- [ ] 功能目录下没有编号子目录
- [ ] progress.md 的"当前状态"与代码实际状态一致
- [ ] progress.md 的 Changelog 追加了本次变更
- [ ] spec.md 的"当前需求"没有过时信息
- [ ] handoff.md 是最近一次 session 的交接信息
- [ ] checklist.md 的验收项与 progress.md 的完成度一致
- [ ] 没有在 Changelog/Decision Log 中修改历史记录
