## 3. S7 答案生成异常分析

S7 从 17.96s 飙升到 132.85s（+639.6%），这是最关键的发现。

### 3.1 可能原因

1. **LLM API 响应时间波动**：两次实验使用相同的 LLM API，但网络延迟可能不同
2. **评估阶段耗时**：S7 的计时包含了 `pipeline.query()` 中的生成步骤，但评估指标计算（faithfulness、answer_relevancy）也消耗大量 LLM API 调用
3. **上下文长度差异**：OCR 关闭后，解析出的文本可能更短，导致检索到的上下文不同，进而影响生成时间

### 3.2 Token 消耗对比

| 环节 | OCR 开 | OCR 关 | 变化 |
|------|--------|--------|------|
| S5 输入Token | 44,556 | 50,106 | +12.5% |
| S5 输出Token | 2,351 | 2,978 | +26.7% |
| S7 输入Token | 38,013 | 34,704 | -8.7% |
| S7 输出Token | 1,290 | 1,795 | +39.1% |
| 总Token | 86,210 | 89,583 | +3.9% |

S7 的输出 token 增加了 39.1%，说明 OCR 关闭后模型生成的回答更长。但 token 变化不足以解释 639.6% 的时间增长。

### 3.3 根因推断

S7 的时间异常最可能的原因是 **LLM API 响应延迟波动**。132.85s / 10次 = 13.3s/次，而正常应该 ~1.8s/次。这可能是 API 服务端负载高导致的。

## 7. 结论

### 7.1 OCR 对性能的影响

| 维度 | 影响 | 量化 |
|------|------|------|
| 解析速度 | 显著影响 | OCR 占解析时间 63.2% |
| 资源消耗 | 显著影响 | CPU -22.5%, 内存 -18.0% |
| RAG 质量 | 无负面影响 | Faithfulness +4.8% |

### 7.2 建议

1. **默认关闭 OCR**：对于有原生文本层的 PDF，OCR 不仅不提升质量，反而降低性能
2. **按需启用 OCR**：仅在检测到扫描件（无文本层）时启用 OCR
3. **智能 OCR 策略**：先检测页面是否有文本层，无文本层时才启用 OCR

### 7.3 预估优化效果

如果采用智能 OCR 策略（仅扫描件启用）：
- 假设 90% 的页面有文本层：S1 从 412s 降至 ~170s，总耗时从 526s 降至 ~285s
- 假设 100% 的页面有文本层：S1 从 412s 降至 ~152s，总耗时从 526s 降至 ~265s
