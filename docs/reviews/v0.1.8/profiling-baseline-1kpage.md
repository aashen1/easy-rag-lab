## 5. 性能瓶颈分析

### 5.1 瓶颈排名

| 排名 | 环节 | 耗时 | 占比 | 瓶颈原因 |
|------|------|------|------|---------|
| 1 | S1 PDF解析 | 412.35s | 78.3% | OCR 开销极大 |
| 2 | S5 测试集生成 | 38.68s | 7.3% | LLM API 等待 |
| 3 | S7 答案生成 | 17.96s | 3.4% | LLM API 等待 |
| 4 | S3 向量嵌入 | 0.33s | 0.1% | 已有 GPU 加速 |

### 5.2 S1 PDF解析深入分析

S1 占总耗时 78.3%，是绝对瓶颈。原因：

1. **OCR 开启**：`use_ocr: True`，`ocr_language: chi_sim+eng`
2. **单页耗时**：0.41s/页，其中 OCR 占主要时间
3. **CPU 密集**：平均 73.3%，无 GPU 加速
4. **串行处理**：12 个 PDF 逐个解析，无并行

**预估 OCR 贡献**：根据 pymupdf4llm 的性能特征，OCR 约占解析时间的 60-80%，即约 250-330s。

### 5.3 S7 答案生成深入分析

S7 单次调用平均 1.796s，其中：

- LLM API 网络延迟：约 0.5-1.0s
- LLM 推理时间：约 0.5-1.0s
- 上下文组装：约 0.01s

Token 效率分析：
- 平均输入：3,801 tokens/问题
- 平均输出：129 tokens/问题
- 输入/输出比：29.5:1（上下文占比 94.1%）

## 6. 优化建议

### 6.1 高优先级（影响 > 50%）

| 优化方向 | 预期提升 | 实施难度 | 说明 |
|---------|---------|---------|------|
| 关闭 OCR | 总耗时 -60% | 低 | 大部分 PDF 有文本层，OCR 仅对扫描件必要 |
| 并行 PDF 解析 | S1 -40% | 中 | 多进程解析，充分利用多核 CPU |

### 6.2 中优先级（影响 10-50%）

| 优化方向 | 预期提升 | 实施难度 | 说明 |
|---------|---------|---------|------|
| 启用 Reranker | FPR -50% | 低 | 过滤无关检索结果，降低噪声 |
| 减少 max_context_tokens | S7 -30% | 低 | 从 8000 降至 4000，减少输入 token |
| 缓存测试集 | S5 -100% | 低 | 已有缓存机制，首次后自动命中 |

### 6.3 低优先级（影响 < 10%）

| 优化方向 | 预期提升 | 实施难度 | 说明 |
|---------|---------|---------|------|
| 增大 batch_size | S3 -20% | 低 | 从 32 增至 64，但 S3 已很快 |
| 使用更快 LLM | S7 -50% | 中 | 切换到更快的 LLM API |
| 调整 chunk_size | 质量 ±10% | 低 | 512→256 或 1024，需实验验证 |
