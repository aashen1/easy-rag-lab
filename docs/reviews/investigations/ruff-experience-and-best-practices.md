# Ruff 经验沉淀：从混乱到规范，以及新项目的正确起步

> 本文档记录本项目引入 Ruff 的完整演进历程，提炼经验教训，并为未来新项目提供"从第一天就用 Ruff"的最佳实践。

---

## 第一部分：本项目的 Ruff 演进史

### 阶段一：无规范期（v0.1.0 ~ v0.1.5）

项目初期没有任何代码质量工具。开发节奏快，功能优先，代码风格完全依赖个人习惯。这一阶段积累的问题包括：

- **import 混乱**：同一个文件中 import 顺序随意，标准库、第三方库、本地模块混在一起
- **未使用的导入和变量**：重构后遗留的 `import` 和赋值语句无人清理
- **类型标注过时**：大量使用 `typing.List`、`typing.Dict` 等旧式写法，而非 Python 3.9+ 的 `list`、`dict`
- **代码风格不统一**：缩进、空行、引号风格因人而异
- **潜在 bug 未被发现**：如循环变量未使用（B007）、盲异常断言（B017）、重复定义（F811）

这些问题的本质不是"写错了"，而是**没有工具告诉开发者什么是对的**。

### 阶段二：手动规范期（v0.1.6）

v0.1.6 进行了"代码质量改进"：类型标注、Docstrings、代码重构。但这次改进完全靠人工审查，没有工具支撑，效果有限：

- 改进了当时注意到的文件，但无法系统性地覆盖所有代码
- 新写的代码仍然可能引入同类问题
- 没有持续保障机制，改进会随时间退化

**教训**：人工审查不可扩展，必须有自动化工具。

### 阶段三：引入 Ruff（v0.1.6 之后，2026-04-21）

在 backlog RF-010 中添加了"lint/ruff 配置"任务，同日完成。配置策略是**初期宽松**：

- 启用规则集：`E, W, F, I, UP, B, SIM`（7 个规则集）
- 全局忽略：`E501`（行过长）、`B008`（默认参数调用函数）、`SIM108`（三元表达式）、`E402`（import 不在顶部）
- 首次扫描结果：**982 个错误**，其中 832 个可自动修复

主要问题分布：
- `UP006/UP007`：旧式类型标注（~40%）
- `I001`：import 排序（~30%）
- `F401`：未使用的导入（~15%）
- 其他：F841（未使用变量）、B007、SIM117 等

**处理策略**：初期不强制修复，后续逐步收紧。按模块逐个 `ruff check --fix` 修复。

### 阶段四：积压问题拖延期（v0.1.7 ~ v0.1.8）

Ruff 成为日常开发流程的一部分，`pixi run lint` 作为每次代码变更的验收标准。但历史积压问题一直存在：

- 每次跑 `ruff-check` 都能看到 15 个左右的错误
- 全部在测试文件中，不影响功能，所以"以后再修"
- 全局忽略的 `SIM108` 和 `E402` 让部分代码绕过了检查
- 发现 lint 盲区：`pixi.toml` 中 ruff task 仅覆盖 `src/ eval/ tests/`，根目录的 `main.py` 和 `interactive.py` 不在检查范围内（后于阶段五修复）

这一阶段的特征是**新代码质量可控，旧代码债务累积**。

### 阶段五：一次性清偿（v0.1.8 之后）

终于决定彻底解决积压问题，同时收紧配置策略：

**配置收紧**：
- 从全局 `ignore` 中移除 `SIM108` 和 `E402`
- 改为按需行级忽略：在具体行用 `# noqa: SIM108` 或 `# noqa: E402` 精准豁免
- 理由：全局忽略会放行所有同类问题，行级忽略只放行确实需要的

**15 个积压错误修复**：

| 规则 | 数量 | 修复方式 |
|------|------|---------|
| F841（未使用变量） | 7 | 去掉赋值或改为 `_` |
| SIM117（嵌套 with） | 4 | 合并为单行 `with A, B:` |
| B007（循环变量未使用） | 1 | 去掉 `enumerate` 或改为 `_` |
| B017（盲异常断言） | 1 | `Exception` → `json.JSONDecodeError` |
| F811（重复定义） | 1 | 删除重复的类定义 |

**移除全局忽略后新增的违规处理**：

| 规则 | 处理方式 | 涉及文件 |
|------|---------|---------|
| E402 ×30 | 每行 import 添加 `# noqa: E402` | `run_eval.py`、`run_experiment.py` |
| SIM108 ×2 | 直接改为三元表达式 | `meal.py`、`semantic_chunker.py` |

**最终结果**：`ruff check` → **All checks passed!** 零错误零警告。

**Lint 盲区修复**：
- 在 `pixi.toml` 的 ruff task 中加入 `main.py` 和 `interactive.py`
- 修复根目录 .py 文件中的 17 个 lint 错误（F541、UP006、UP035、B905、F841）

### 演进时间线

```
v0.1.0~v0.1.5  ████████████████████  无规范期：982 个问题积累
v0.1.6         ██                    手动规范：治标不治本
```

## 第二部分：经验教训

### 教训 1：越晚引入，成本越高

本项目在积累了近 1000 个错误后才引入 Ruff。修复这些错误需要：
- 理解每个错误的含义
- 判断是真正的问题还是误报
- 逐个修复并确保不破坏功能
- 处理全局忽略与行级忽略的策略选择

如果在项目第一天就引入 Ruff，这些问题会在写代码的瞬间被捕获和修复，成本接近零。

### 教训 2：全局忽略是隐性债务

`SIM108` 和 `E402` 被全局忽略后：
- 开发者不再意识到这两条规则的存在
- 新代码中本应修复的 SIM108 违规也被放行
- 直到移除全局忽略时，才发现 `meal.py` 和 `semantic_chunker.py` 中有本应修复的违规

**原则**：能用 `# noqa` 行级忽略解决的，不要用全局 `ignore`。全局忽略只用于确实在项目中普遍不适用的规则（如 E501、B008）。

### 教训 3：Lint 盲区是定时炸弹

本项目 ruff task 仅覆盖 `src/ eval/ tests/`，根目录的 `.py` 文件不在检查范围内。这意味着：
- `main.py` 和 `interactive.py` 可以包含任何代码质量问题而不被发现
- 随着这些文件增长，问题会越来越难修

**原则**：ruff 的检查范围必须覆盖所有 Python 源文件，不留盲区。

### 教训 4："以后再修"永远不会修

15 个 lint 错误在测试文件中存在了多个版本，每次看到都是"不影响功能，以后再修"。直到有人专门安排时间清理，才一次性解决。

**原则**：lint 错误应该在出现的当天修复，而不是加入"技术债务"列表。pre-commit 钩子可以强制执行这一点。

## 第三部分：新项目 Ruff 最佳实践

### 第一步：项目初始化时同步配置 Ruff

在创建项目的 `pyproject.toml` 时，同步添加 Ruff 配置。不要等到"代码写多了再补"。

### 推荐的默认配置

```toml
[tool.ruff]
target-version = "py312"
line-length = 88

extend-exclude = [
    "data",
    ".pixi",
    ".venv",
]

[tool.ruff.lint]
select = ["E", "W", "F", "I", "UP", "B", "SIM"]
ignore = ["E501"]

[tool.ruff.lint.per-file-ignores]
"__init__.py" = ["F401"]

[tool.ruff.format]
quote-style = "double"
indent-style = "space"
```

**配置说明**：

| 配置项 | 值 | 理由 |
|--------|-----|------|
| `select` | `E, W, F, I, UP, B, SIM` | 覆盖错误检测、风格检查、import 排序、新版写法、bug 模式、简化建议 |
| `ignore` | 仅 `E501` | 行过长由 formatter 处理；其他规则不要全局忽略 |
| `per-file-ignores` | `__init__.py` → `F401` | init 文件的职责是重新导出，未使用导入是预期行为 |
| `line-length` | `88` | black 默认值，社区最广泛使用的标准 |
| `target-version` | 按实际设定 | 让 Ruff 不建议不兼容的语法 |

**关于 `ignore` 的原则**：

- ✅ `E501`：formatter 会自动折行，linter 不需要重复检查
- ✅ `B008`：**仅在使用 FastAPI 时添加**，其他项目不需要
- ❌ `SIM108`：不要全局忽略。如果某处 if-else 确实更清晰，用 `# noqa: SIM108` 行级忽略
- ❌ `E402`：不要全局忽略。如果某处 import 必须延迟，用 `# noqa: E402` 行级忽略
- ❌ 其他规则：先不要忽略，遇到真正需要忽略的再按行处理

### 第二步：配置 pre-commit 钩子

```yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.11.6
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
```

**效果**：每次 `git commit` 自动检查和格式化，不合格的代码无法入库。

### 第三步：配置开发任务

在包管理器中定义快捷命令（以 pixi 为例）：

```toml
[tasks]
ruff-check = "ruff check src/ eval/ tests/"
ruff-format = "ruff format src/ eval/ tests/"
lint = "ruff check --fix src/ eval/ tests/ && ruff format src/ eval/ tests/"
```

**关键**：ruff 的检查路径必须覆盖**所有** Python 源文件目录，不留盲区。

### 第四步：与 Ruff 互动的最佳实践

#### 日常开发流程

```
写代码 → 保存 → git add → git commit
                              ↓
                        pre-commit 自动运行
                              ↓
                    ┌─────────┴─────────┐
                    ↓                   ↓
               ruff check          ruff format
               发现问题？          格式不对？
                    ↓                   ↓
               自动修/报错         自动修好
                    ↓                   ↓
                    └─────────┬─────────┘
                              ↓
                        文件被修改？
                         ↓         ↓
                        是         否
                         ↓         ↓
                    commit失败  commit成功
                    重新add
```

#### 遇到 Ruff 报错时的决策树

```
Ruff 报了一个错误
       ↓
是真正的 bug 或代码质量问题吗？
       ↓
   ┌───┴───┐
   是      否
   ↓       ↓
 修复它   这个建议合理吗？
   ↓      ↓
 完成    ┌──┴──┐
        合理  不合理
         ↓     ↓
      接受   用 # noqa: RULE 忽略
      建议   并在旁边注释原因
```

#### `# noqa` 使用规范

1. **精确指定规则**：用 `# noqa: E402` 而非 `# noqa`，避免意外忽略其他规则
2. **就近忽略**：只忽略出问题的那一行，不要用全局 `ignore` 或 per-file-ignores 代替
3. **注释原因**：对于不明显的忽略，在 `# noqa` 旁加简短说明
   ```python
   from src.meal import MealConfig  # noqa: E402  # needs sys.path.insert above
   ```
4. **定期审查**：全局搜索 `# noqa`，确认每个忽略仍然必要

#### 何时考虑全局忽略

只有满足以下**全部条件**时才考虑全局忽略：
1. 该规则在项目中**普遍**不适用（不是偶尔几处）
2. 行级忽略会导致大量重复的 `# noqa` 标注
3. 忽略该规则不会掩盖真正的代码质量问题

典型例子：`E501`（formatter 自动处理）、`B008`（FastAPI 项目）。

### 第五步：渐进式收紧策略

如果项目已经有一定规模，可以分阶段启用规则：

| 阶段 | 启用规则 | 目标 |
|------|---------|------|
| 第 1 周 | `E, W, F` | 修复真正的错误和风格问题 |
| 第 2 周 | `+ I` | 统一 import 排序 |
| 第 3 周 | `+ UP` | 升级到新版 Python 写法 |
| 第 4 周 | `+ B, SIM` | 启用 bug 模式检测和简化建议 |

每个阶段用 `ruff check --fix` 自动修复能修的，手动处理剩余的，确保零错误后再进入下一阶段。

## 总结

| 场景 | 推荐做法 |
|------|---------|
| 新项目 | 第一天就配置 Ruff + pre-commit，使用推荐默认配置 |
| 现有项目引入 Ruff | 宽松起步，渐进收紧，不要试图一次性修复所有问题 |
| 遇到不认同的规则 | 优先用 `# noqa: RULE` 行级忽略，而非全局 ignore |
| 积压的 lint 错误 | 安排专门时间一次性清偿，不要让"以后再修"成为常态 |
| Lint 盲区 | 确保检查路径覆盖所有 Python 源文件 |
