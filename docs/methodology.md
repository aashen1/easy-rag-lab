## 概述

"抛接球年轮"是一套适用于 AI 辅助开发项目的版本演进管理方法论。它将传统的版本管理理念与 AI 时代的开发特点相结合，形成了一套清晰、可追溯、易于维护的文档体系。

### 核心理念

1. **文档是意图源码，代码是编译产物**
   - 在 AI 辅助开发中，Spec/Roadmap/决策文档是"给 AI 编译的意图"
   - 文档的重要性应高于传统实践

2. **版本演进形成"年轮"**
   - 每个版本的开发历程形成清晰的"年轮"记录
   - 便于追溯决策背景、理解代码演变

3. **抛接球式迭代**
   - 抛球：创建版本 Spec/Feature Plan（意图）
   - 接球：AI 生成代码，人工验收
   - 复盘：生成 outcome 文档（承诺 vs 交付 vs 调整）
   - 归档：形成项目"年轮"

4. **文档即记忆**
   - 文档系统是项目的跨 session 记忆系统
   - 每个 AI session 都是 stateless 的，唯一延续性来自文档
   - 读写分离：读记忆理解状态，写记忆延续进度
   - 详见 `project-memory` skill

## 文档体系结构

### 核心文档

| 文档 | 位置 | 用途 |
|------|------|------|
| **版本演进年轮** | `docs/version-history.md` | 记录所有版本的迭代历程，作为"年轮"的总入口 |
| **待做事项总表** | `docs/backlog.md` | 项目"卫生情况"的总入口，追踪所有待做事项 |
| **版本验收报告** | `docs/reviews/vX.X.X/` | 每个版本的代码审查、交付对照、下版本方向 |

### 版本验收报告组成

每个版本目录（`docs/reviews/vX.X.X/`）包含：

| 文档 | 用途 |
|------|------|
| `code-review.md` | 发版后的全面代码审查，分析实现质量、发现 bug、提出重构建议 |
| `outcome.md` | 承诺 vs 交付对照表，记录哪些实现了、哪些降级了、哪些延期了 |
| `next-direction.md` | 下版本的开发大方向、主要 feature、注意事项 |

## 版本发布流程

### 1. 发版前

- 检查所有 active 文档与代码的一致性
- 确认 `docs/backlog.md` 中的待做事项状态

### 2. 发版后（抛接球循环）

```
┌─────────────────────────────────────────────────────────────┐
│                      发版                                    │
└─────────────────────────────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 1: 代码审查                                            │
│  创建 docs/reviews/vX.X.X/code-review.md                     │
│  - 分析实现质量                                              │
│  - 发现 bug 和重构建议                                        │
│  - 识别"建议单开"的大型任务                                   │
└─────────────────────────────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 2: 打扫卫生                                            │
│  - 修复 code-review 中的小 bug                               │
│  - 落实小型重构建议                                          │
│  - 更新 docs/backlog.md（添加"建议单开"的内容）               │
└─────────────────────────────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 3: 交付对照                                            │
│  创建 docs/reviews/vX.X.X/outcome.md                         │
│  - 承诺 vs 交付对照表                                        │
│  - 记录技术债和认知偏差                                       │
│  - Prompt 优化记录（供下一轮迭代）                            │

                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 4: 拟定下版本方向                                       │
│  创建 docs/reviews/vX.X.X/next-direction.md                  │
│  - 版本主题                                                  │
│  - 主要 Feature                                              │
│  - 注意事项                                                  │
└─────────────────────────────────────────────────────────────┘
                           │

┌─────────────────────────────────────────────────────────────┐

│  - 引用验收报告                                              │
└─────────────────────────────────────────────────────────────┘
                           │
                           ▼
                      下一版本开发
```

## 待做事项管理

### `docs/backlog.md` 的作用

作为项目"卫生情况"的总入口，集中追踪所有非阻塞性质的 bug/feature/refactor。

### 与 code-review 的关系

- code-review 中"建议单开"的内容**必须**同时添加到 `docs/backlog.md`
- backlog.md 中的条目引用来源文档，便于追溯上下文
- 完成后更新状态，保留历史记录

### TODO ↔ Backlog 双向异步机制

`TODO.md` 和 `docs/backlog.md` 构成双文档 issue 追踪体系：

| 文档 | 管理者 | 性质 | 内容 |
|------|--------|------|------|
| `TODO.md` | 人类 | 随笔式待办笔记 | 开发者随时记录的改进思路 |
| `docs/backlog.md` | AI | 结构化 issue 追踪 | 按 Bug/Feature/Refactor/Optimization/Investigation 分类的正式 issue |

#### 归档流程（单向：TODO → backlog）

```
人类在 TODO.md 写下新 issue（- [ ] 格式）
    ↓
AI 检测到未归档的 issue
    ↓
分类 + 分配 ID → 写入 backlog.md
    ↓
在 TODO.md 原条目后追加归档时间戳：📋 YYYY-MM-DD 归档为 [RF-007]
（不删除原内容，不打钩，不移动位置）
```

#### 完成同步（反向：backlog → TODO）

```
backlog.md 中某 issue 标记为 ✅ 已完成
    ↓
下次归档检查时，AI 发现 TODO.md 中对应条目已归档但未打钩
    ↓
打钩 + 追加完成时间戳：✅ YYYY-MM-DD 该issue已确认完成
    ↓
将条目移动到对应完成日期的标题下
```

#### TODO.md 条目状态标记

| 状态 | 标记格式 | 含义 |
|------|---------|------|
| 新建 | `- [ ] 描述内容` | 人类刚写，AI 尚未归档 |
| 已归档 | `- [ ] 描述内容 📋 2026-04-21 归档为 [RF-007]` | AI 已归入 backlog |
| 已完成 | `- [x] 描述内容 📋 2026-04-21 归档为 [RF-007] ✅ 2026-04-22 该issue已确认完成` | backlog 已完成，同步回 TODO |

#### 触发方式

- **自动触发**：每次对话开始时，AI 检查 TODO.md 是否有未归档 issue
- **手动触发**：用户说"打扫卫生""归档TODO"等指令

#### 日期标题结构

每个日期标题下包含 summary 和 verbose 两个子节：

- **verbose**：人类原始表述 + AI 追加的时间戳
- **summary**：AI 根据 verbose 生成的简洁摘要

### ID 命名规范

- Bug: `BUG-NNN`
- Feature: `FEAT-NNN`
- Refactor: `RF-NNN`
- Optimization: `OPT-NNN`
- Investigation: `INV-NNN`

## 聊天记录入库流程

### 收件箱机制

```
docs/inbox/          # 待处理文档收件箱（用户放入聊天记录）
    ↓
AI 检测并提示处理
    ↓
入库处理（评估→精简→命名→存放→更新关联）
    ↓
docs/inbox-log.md    # 记录处理结果
    ↓
docs/inbox-processed/ # 已处理的原始文件（定期清理）
```

### 入库检查清单

1. 评估文档价值，决定是否入库
2. 精简内容，只保留核心信息
3. 规范文件名（英文、小写、连字符）
4. 添加元数据（来源、日期、关联）
5. 放入合适目录
6. 更新 backlog.md（如有待办事项）
7. 删除原始聊天记录

## 与传统版本管理的区别

| 方面 | 传统版本管理 | 抛接球年轮 |
|------|-------------|-----------|
| 文档重要性 | 次要，代码为主 | 核心，文档是意图源码 |
| 版本记录 | CHANGELOG 为主 | 年轮 + 验收报告 |
| 待做事项 | Issue Tracker | backlog.md + 来源引用 |
| 发版流程 | 发布 → 下一版本 | 发布 → 审查 → 打扫 → 复盘 → 下一版本 |
| AI 协作 | 无 | 收件箱机制 + 文档入库流程 |

## 实施建议

1. **从非核心模块试点**：先在一个非核心模块跑通完整流程
2. **保持轻量**：不要创建不必要的文档，简化生命周期管理
3. **增量迭代**：一次只引入一个优化手段，便于定位问题
4. **数据驱动**：每次优化前后都要运行评测，量化改进效果
