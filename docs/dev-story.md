刚刚开了个 AI 对话，它的分析说这个项目已经有五万行代码，我翻看了一下它的思考过程，用的是这个指令：

```bash
find <路径名称> -name "*.py" -exec wc -l {} + | sort -rn | head -20
```

还挺高级，一下子就列出来了。

目前是`v0.1.13`版本，这个项目里有 20992 行`src/`代码，构建核心 RAG 程序和一些其他功能；10504 行`eval/`代码，负责 RAG 评估系统；25734 行`tests/`代码，和功能代码几乎一样多，这是因为我在建库的时候，找 Claude 要了一份`CLAUDE.md`，它在里面说“一定要有测试，测试与源码一一对应”。

于是这么半个月下来，这孩子硬是给我写了整整 1509 条非集成测试，和 10 条真实调用 API 的集成测试。跑一遍这一千五百条测试，就得花去半分钟时间，每次 merge 都要等它跑。这种夸张的测试量不免让人感到疑虑，是否是为了测试而测试呢？不知道，没写过这种项目级代码，问AI它也是说“这些都是必要的测试”，那就暂且先这样吧。

如今，这个项目已经很大，里面的功能已经很多，但是在即将把它敲定为稳定版，然后开源并写上简历的时间点，我对它的疑虑却也在无限放大。

## AI 编程的演进

2026 年，一个对编程一窍不通的人，凭借着最好的大模型，到底能不能直接发挥出比肩一名 2022 年以前传统程序员的功力？

这个项目的五万行代码，虽然没有精确的数据，但我相信应该有超过一半出自`GLM-5.1 (in TRAE CN)`的手笔，这即使不是当下最好的模型，也一定可说是**很好**的模型。余下的一小半代码当然也不是我写的，而是 `GLM-5、Qwen-3.6Plus、Kimi-K2.6` 等其他模型，它们接力合作完成的。

在我的印象里，我的文字输入主要都是 prompt 和改配置，真正由我**写**的代码，有没有一百行都要打个问号。

我自认是一个纯粹的、毫无基础的非科班，在二月份开始准备求职~~（结果稀里糊涂自己死磕了一个月力扣，Hot100才做了一半，大家不要学我，该背答案还是得背）~~之前，我前几次自己想写代码，也就是大一的 C 语言课、大二大三的 Python 通识课、还有闲着没事学 Unity 和 Cocos 的时候的一些教程代码（学完教程也都没了下文）。

我一直提供给AI关于我编程能力的一句形容就是，“我基本没有写过两百行以上的函数，也没有接触过算得上‘项目’的代码，你看着办”。

那时候看着教程，一点一点敲，C 语言课里一个链表在那里来回琢磨，好像用的还是一个非常复古的紫色 logo 的 IDE，因为 VS Code 运行 C 代码让我感觉有点头大，所以当时没用明白。

然而 2026 年的今天，我花了满打满算不到半个月时间，从建立一个空的 repo 到里面堆着三万行功能代码和两万行测试代码，我所做的事情就是不断地问 AI，“我需要这个，你能不能写？”和“有这个问题，你能不能修？”，然后静等神迹降临。

这种行为，在几年前有一个新潮的名字，叫“Vibe Coding”，如果要用中文称呼，可以译作“氛围编程”。

我对这个名字的理解是：你要的不是技术，而是一个气氛，一种感觉。在对话框里对它指指点点，它就出来代码，你粘贴进 IDE（最早的时候，AI 还没有这么深度地耦合到 IDE 里，大部分人还是在网页端要来代码，自己贴到本地点运行），跑一跑，要么成功，要么跑不起来然后再问一轮直到成功。

后来大家发现这样子弄出来的代码，很多时候都沦为一次性的，难以维护，难以扩充，甚至很快就难以看懂。AI在上面不停地打补丁，打补丁，最后死活也改不明白，用户先失去了耐心，整个推倒重来。

于是“Vibe Coding”在近几年明显就提得少了，更多是作为贬义词出现，连带着“Vibe”这个词在中文互联网上完成了“没人认识（至少我以前是不认识）→众人追捧→人见狗嫌”的快速语义进化。

大家开始琢磨如何“统驭”这个强大的存在，接力而来的是各种 Agent、Claw、Harness，以及现在好像 Harness 后面又有什么新词儿了。大家开始琢磨的问题从“该写什么代码”转向了“不该写什么代码”和“写什么样的代码”。

聚光灯下的产品也从 Claude Code 移到 OpenClaw，然后是近期的 Hermes，过不久可能又会有新的名角儿。

Agent 时代来到了，也不再需要去网页复制粘贴了，我们有 Copilot，有 Cursor，有 Claude Code，当然也有国产的一众竞品，其中就有本项目的核心开发工具，TRAE CN。它们会写代码，会写很多、很长、很高级也很复杂的代码。能自己跑，看 bug，查网页，读文档，学API，不跑通就不停下来。

最早一个网页对话，撑死不过几百行；现在随便一个 AI 助手，吐个成百上千行不成问题；而在基模组的实验室里，动辄是以小时为单位的长线工作，对着一个项目代码不停地改不停地提点，好像是已经成为了新的演进方向之一。

纵观这几年的 AI 编程，能很明显地感觉到“每次产出代码”的“粒度”越来越大了。一个提问所能生成的东西，从一段代码，一个函数，一个模块，到一个 feature，一个项目，一个……软件？

在这其中，人的角色似乎是越来越小了。我记得GLM发的那个报告，人家大模型自己在那里闷头写码，就能把结果的数值提得越来越高。OpenAI 的那篇报告（[工程技术：在智能体优先的世界中利用 Codex | OpenAI](https://openai.com/zh-Hans-CN/index/harness-engineering/)），也是说AI的作品已经具备百万行级别的产出。

> 上面这篇报告我直到写到这，才第一次打开来扫了一遍原文，前面都是停留在道听途说。读了之后还是感触挺深，发现这差不多是我这半个月开发模式的完善版，甚至一定程度上可以推翻掉我这篇随笔的论调。不过报告全文信息密度很高，短时间有些消化不过来，所以先按下不表。或许下个项目可以多多结合下 OpenAI 的实践经验。

这种时候，还要人干什么呢？我经常开玩笑说，随着这些 Harness 什么的技术趋于成熟，以后那些公司就每天去把服务器的电源插上，然后就可以锁门下班了。不过回头想想，其实连这都不需要——为什么要每天去插电源，只要电费交好不就行了吗，让它自己一年干到头好了。

这样的话，确实是形成了与 HITL 相对的一种流程：人不在回路（Human-Out-Of-The-Loop）。

不过在此之前，我还是想记录一下，我在这半个月开发过程中的一些对于“AI做不到的”的感想。

## AI 代码的缺点

在我开始大谈特谈“我所知的 AI 代码缺点”以前，首先要叠个甲。我的认知基本来源于 TRAE CN 当中以 GLM-5.1、GLM-5和 Qwen-3.6Plus 等为代表的国产模型，结合各家网页端免费版对话的表现。

我确实没有接触过老美的顶级模型，因为太抠门，舍不得那钱。

在我所观察到的这些模型当中，有一个点我觉得很值得提，就是“选方向”。

我不否认，作为一个对“技术选型”完全没有经验的人，这个项目中的所有技术决策几乎没有我亲自操刀的。什么实现细节，什么工厂模式，统统都是 AI 的大作。

但是我仍然感觉到，这种方式是不够的（再叠一遍：我不知道现在最强的模型能做到怎样，这些判断都是基于我使用到的这些模型的表现，以下不再赘述）。

飞天闪客老师有个科普视频，里面“AI出门”的那个桥段我觉得相当形象。它就像一头力大无穷的倔牛，知道是那个方向，也知道怎么“扫除障碍”，于是就闷着头往那边顶，木头箱子也顶，水泥墩子也顶。全部顶穿了，跟你说，“我做完了”。

当然实际上，现在的 AI 已经相当聪明，一般不会顶到水泥墩子这么极端的阻碍，甚至很多时候因为它渊博的知识，所做出的技术决策要比人聪明得多。

比如这个项目当中有一个 Artifacts 功能。试想 RAG 链路从 PDF→文本→切块→嵌入→……，当中每一环其实都是一个中间产物。那比如我现在就想试试看换不同的嵌入模型，对比其效果，其他环节都不改变。那么 chunk 及其之前的结果都是可以复用的。这种东西该怎么设计呢？

我把这个想法给 AI 一提，它很快告诉我，在编译技术当中已经有一套成熟的实践，就是用来管理那些编译过程中不变的东西，它叫 Artifacts。我看后觉得大为惊奇，点了确认之后，很快一套用哈希当指纹的东东就实现出来了。

如果让我自己想怎么去写，还真不知道要想多久，也不一定能知道有这个东西，最后做出来也不一定有这个好用。

但是同样它也有我嫌不够机灵的时候。就比如刚刚做的 Streamlit 界面，让它在里面弄一个 PDF 预览，一开始效果可以，但是是一个额外弹窗。我要求加入页码跳转功能之后，突然发现风扇开始呼呼转，于是要求它优化性能。

> 事后我发现，那个时间点微软遥测正好起来了，所以不排除是误伤，之后有兴趣可以测一下

结果这家伙把 PDF 浏览改成了 PPT一样的，一次渲染一页，用箭头翻页，给我看乐了。

后来又调整了几轮，最后它终于弄明白怎么整出一个像 Edge 内嵌 PDF 浏览器一样的东西，我也让它写了一篇踩坑手记。

总的来说，这半个月的开发给我的感受是，目前（至少在我本次项目使用的开发套件中），人在回路还是必要的选择。甚至于这个项目在今天给我极深的疑虑，我认为相当的原因就是人的参与太少了。

因为犯了急于求成的错误，AI 给出来的 plan 文档和 spec 文档，我经常是扫几眼就点了通过，很多都没有细看，从而偏离了 plan/spec 模式的“先确认再执行”的原意，只是把文档作为一种“留痕”的手段。

但今天随着我把它的功能往稳定版打磨，我不断地注意到其中一些配合不够紧密的地方，又要回过头去进行深度的挖掘与重构。

下个项目我大概会增加“看”的时间，稍微放慢一点脚步，在它开始狂奔之前多问问其中的一些决策细节。尽管我没有软件开发的什么系统经验，但很多时候只要以普通人的认识提出来问题，AI自己就能纠正其中“感觉不对”的一些地方。

当然了，或许更强的模型在“感觉”这方面已经有所改善，等那种模式全面铺开的日子，这个判断估计也要随之而变了。

## 我对这个项目的评价

今天早上让AI审核了一下，它给的评价是屎山评分 3/10（1分为完美代码），“轻度屎山”。

提出的问题主要是一些长度过大的文件，一些没有复用的写法等。随后我安排了一个spec，现在说是都已经拆分整理完了，不过还没有验收合并。

但是——在我体感来看，这个项目即使经过了重构而挑不出风格上的毛病，它的“方向”仍然有一些问题，是可以启发我接下来新的编程实践的。

### 一、功能膨胀没有节奏

所谓软件，功能一般是会随着开发越来越丰富。但是在功能变得越来越廉价的年代，“做一个功能”变得非常容易，而“不做这个功能”或许才是我们要判断的东西。

我在社区上听到过一个例子：OpenClaw。这是 2026 年开年风头无两的明星产品，然而我自己因为各种顾虑而没有真正使用过，因此也只能是拾人牙慧，转述一些我听来的二道消息。

OpenClaw 开发者的哲学是相当激进的，因此 OpenClaw 的功能膨胀速度也是空前的，听说一个主 TypeScript 就有几万行代码。

> 很抱歉这篇随笔中充斥着大量“听说”“好像”“似乎”等不确定的词语，因为我写作时基本是想到啥写啥，很多看新闻和社区讨论知道的新进展，实在是还没有时间去一一核验，如果您对某些说法感到疑虑，不妨让 AI 打开网页搜索，进行一次事实核查。

不过目前来看，它的开发团队应该是弄明白了如何“乱中取定”，所以尽管有一些对于它“屎山”的批评，OpenClaw 仍然是很多场景下的“实用”选择。

有不少以轻量级为卖点的其他 Claw，不过大概都没能撼动它开山老祖的地位；后来的 Hermes 也是与它占据了存在差异的另一生态位，并没有说直接就把 OpenClaw 拉下神坛。

我们是否应该学习 OpenClaw 的这种开发节奏呢？我目前认为还是不妥。

它的快速迭代是与它明星产品的定位互相促进，使得它被社区推着，越火就更新得越快，更新越快就越火。项目在混沌中快速壮大，中间也出现过改名风波，安全风波等等，算是在特殊时点的一个特殊产物。

等到 Hermes 一出来，与它可以说形成了一个张力，体现出“重”与“轻”的区别。

一个软件“功能很多”，当然可以作为一大卖点。比如我读过一篇比较它俩的文章，就说 OpenClaw 对于需要接入各种 IM （即时消息）软件，比如 QQ、微信、钉钉、飞书……它的接口是很完善的，这当然就是它功能膨胀所带来的一个好处。而 Hermes 则没有这个优点（文章观点，有待验证），而是被形容为了一种“小而美”的新一代产品，把持着一种更加有“格调”的自进化哲学。

但是“功能很少”同样也可以是卖点。就像 AI 时代 SaaS 为什么挨了一记，就是说很多长期维护的软件，里面相当多的功能其实并不都是需要的，而 AI 能够在明确需求之后，量体裁衣地开发一个“刚刚好”的软件，所以对 SaaS 形成了一种冲击。那么我们是否可以汲取这个经验，在写 AI 代码的时候想得更加“克制”一些，或许最终的成品会更加“恰当”？

### 二、技术选型不够审慎

这个问题则是和“token焦虑症”相联系的。现在的模型厂很多都有 token 套餐，定期定额，用不完浪费。于是大家会时刻在意着，要把token“用完”。本项目也是有类似的心理：GLM-5.1 的排队情况只在深夜比较畅通，等到天一放亮，然后八点左右大家起了床开了电脑，等待人数就噌噌噌往上涨。

于是为了尽量使用最强的模型，在这半个月的每个深夜，我切换成了夜班模式，尽最大努力让夜里两点到上午八点的这一段时间当中，三个 TRAE CN 窗口（对应三个 worktree，因为目前 TRAE IDE 还未原生支持）同时都有活跃的编码任务在进行当中。

> 补一句，这其实造成了相当程度的 token 浪费，按理说很多小任务其实更旧的模型也完全能胜任。不过为了图一个安心感，还是尽量全都上了 GLM-5.1，罪过罪过。

这大概也算 AI 时代一种特有的焦虑，焦虑于“空转”，就像玩模拟经营游戏的时候，看见游戏里的刁民闲下来就着急上火，一个意思。

但是在目前来看，如果规范搭建得不够牢靠就拼命地推动开发任务，尽管 token 是不浪费了，但是项目的“走形”问题却会更快显现出来。

例如本项目中，为了让大模型根据转换后的数据源生成 RAG 问答数据，就要解决“怎么把源数据喂过去”的问题。

最开始 AI 自己琢磨，弄了个办法是直接截断前 8000 字符投过去；后来我发现了这事，觉得不对，让它改成随机抽取 8000 字符的选段，于是 AI 设计了一个叫“segment”的文本尺度；

但是后来我一直修这个合成数据的功能死活修不好，出来的问题集总有各种bug，于是昨天夜里终于挑了一段时间，和 AI 一边讨论一边让它仔细审了审，察觉出来这个 “segment” 的设计想法带着一点补丁的性质，导致 expected_chunks 的命中上总是有点儿问题。

于是我跟它唠了几轮，把 segment 这个概念重新放到与 page、chunk 这两个原有的层级更加契合的一种位置上，进行了一轮重做。希望接下来能改善这个卡了我好多天的问题。

> 刚刚读了 OpenAI 的 Harness 报告，里面提到“**我们经常看到单次 Codex 运行在单个任务上持续工作超过六个小时（通常是在人类睡眠时间）**”，真羡慕啊……我做这个项目真是跟着 AI 连轴转了半个月，不停地轮流指挥各个会话，真是人比 AI 还要累。

### 三、演进轨迹不够清晰

如果您看到的项目库里，到 v0.1.13 有将近一千个提交，那么这应该就是我真实的开发痕迹，未经 git archive 清洗的。我通过 rules 的方式要求 AI 及时做好拆分，“按照最佳实践来做”。但实际上，我也不知道什么叫最佳实践，只能这么吩咐一下，然后希望它能做好。

目前来看应该还算没有失控，至少 AI 自己是能看明白这个项目的演进历史的。至于人能不能看……反正我是没有看那几百个 commit 的欲望。

项目伊始，我在和 AI 讨论开发原则的时候提过一个比喻：

“AI 文档相对于代码，不就有些类似代码相对于汇编么？ AI 担任一种不那么精确但大体方向没问题的高级编译器，把人类语言转换为程序语言。”

根据这个原则，本项目的提交采取了一个“反模式”的做法：提交所有开发过程中的痕迹文档。我会有意识地使用 plan 和 spec 模式，将一大部分“有一定规模的会话”“到底是在做什么”给纳入版本管理。这么做的愿景是希望能方便后面的随时追溯，在 [methodology](methodology.md)  这份文档中被我比喻为“年轮抛接球”。

“年轮”，是版本功能一圈一圈向外扩充的痕迹；“抛接球”，是每次新的 feature branch 派出去到做完回来的一个 round。

这套愿景我还是比较喜欢的，不过实操下来，它对 AI 的约束力还是不够强，这套做法很多时候也未能贯彻到底。比如文档系统用久了，难免堆积着各种 archived docs，你说它是痕迹吗？确实是。但你要说它有什么用？好像也没那么有用。

写完这篇随笔之后，在正式开源之前，我打算把文档系统深度整理一下，至少弄得漂亮些，就像好多家不同的 AI 在分析我的项目开源前准备时，不约而同都提到的一个词：**策展 (curate)**。

这套文档系统是被我自己寄予厚望，希望它能担当起“项目级记忆”的一个重要角色，能够维持长时开发中项目的风格不走形。不过这个项目里，它还是没完全接住这个担子，下次继续努力。

关于演进轨迹方面的一些教训：

1. 如果要使用文档做管理，还是要强调把文档做好验收，放对位置。事先决定一个清晰的 docs/ 结构，比如可以参考 OpenAI 的 Harness 报告里面的那套，他们打磨过后的应该比我这个边做边想的要更成熟。我这个项目过上两三天就会发现积压了一堆历史对话文档，让 AI 去“好好整理”，它也整得不明不白的，估计还是要我自己来过一遍，在手动整理的过程中总结一下合理的归档方式。
2. 发版。这个经验另外有一篇文档专门讨论，就是本项目原本把“修好评测链路”作为 v0.1.9 的主旋律，结果硬是一周左右都没修好，堆积了五六个版本的其他开发内容，还得回过头去让 AI 做整理和补充发版。关于每个版本到底要做什么，这个事还需要更多的考虑。
3. 分支。我看到 OpenAI 他们的做法似乎是 worktree+PR，提到“每个 PR 的生命周期极短”。不过本项目没有那么高端，主要是人工维护着三个长期存在的 worktree，通过 git 分支管理不断地同步。说实话这个效率还是挺低的，例如三个功能分支以何种节奏稳定地同步到 dev，这个操作方式还没有想到特别顺手的。如果都用 merge，历史图会比较丑；但如果用 rebase，那么来来去去的要反复打指令，也很麻烦（或许可以通过脚本优化）；至于 squash，本项目目前没采用过，因为还没有借助到 GitHub 的 Issue 和 PR 系统，下次引入了的话可以考虑考虑。

### 四、但仍不失为一次可贵的实践

缺点挑完说优点。

尽管有着这样那样的问题，但半个月不到能搓出这么一个“像样”的项目，对我个人来说确实是很宝贵的经历，像是打了一场单机黑客松。

（话说我还从来没有正经打过 Hackathon，因为一直嫌弃那种几天熬大夜的节奏。结果做这个项目却为了避开排队高峰，硬是昼伏夜出干了半个月，令人感叹）

随着这个项目的成长，这半个月里我也算成长了许多。除了知道了许许多多计算机领域的技术（一遇到陌生概念就开对话问 AI，在此特别感谢 [Qwen Studio](https://chat.qwen.ai/) / 原 Qwen Chat，提供了方便的对话历史下载功能），还尝试了很多新鲜玩意儿，比如 ruff、pre-commit、loguru、pytest 等等，比如用熟了原来一知半解的 git merge、rebase 和之前听都没听过的 worktree，这些经验都是可以迁移，并且会随着越来越多项目经验，被打磨得越来越好的。

下一个项目依旧是为了撑简历而准备的项目，现在已经在抽空和 AI 讨论中，目前定下是用一周时间去做，在五一假期结束能出一个初版，希望不会又被拖进 issue 地狱里面。

OK，差不多了，打字打得手都疼了，搁笔于此吧。在此也祝我自己，以及祝各位还在挣扎的朋友们，早点儿找到心仪的暑期实习，春秋招顺利。
