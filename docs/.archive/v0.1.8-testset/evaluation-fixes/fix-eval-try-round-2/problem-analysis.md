## 三、详细问题分析

### 3.1 问题集快照缺失（🔴 最严重）

**现状**：
```
test_sets/None.json 内容：
{
  "name": null,
  "strategy": null,
  "num_questions": 10,
  "created_at": null,
  "meal_data_id": null
}
```

**影响**：
- 无法知道这 10 个问题是如何生成的
- 无法复现相同的问题集进行对比实验
- 问题质量无法回溯审核

**根本原因推测**：
- 问题集生成后没有正确写入快照
- 或者写入时某些字段为 None 未被正确处理

### 3.2 检索指标异常（🔴 可信度危机）

**Hit Rate = 1.0 的问题**：
- 10 个问题全部命中，这在 5000 页的大规模数据集上**极不可能**
- 正常生产级系统应该有一定的召回率波动
- 可能是**问题生成泄露了答案信息**，或者**ground truth 设置过于宽松**

**FPR = 1.0 的误解**：
```json
"avg_false_positive_rate": 1.0
```
- 报告中解释为"无误检"，但 **FPR (False Positive Rate) 的定义是：负样本中被误判为正的比例**
- FPR = 1.0 实际表示**所有负样本都被误判为正**，即 100% 误报率
- 这里存在**概念理解错误**或**指标计算错误**

### 3.3 expected_chunks 过度泛化（🔴 严重 Issue）

**问题详情**：
- q001（关于宫颈癌一线治疗方案）标记了 **14 个** expected_chunks：
  - `2025中国宫颈癌诊疗现状白皮书_003` 到 `2025中国宫颈癌诊疗现状白皮书_011`
  - `2025中国宫颈癌诊疗现状白皮书_020` 到 `2025中国宫颈癌诊疗现状白皮书_022`
  - `2025中国宫颈癌诊疗现状白皮书_035` 到 `2025中国宫颈癌诊疗现状白皮书_037`

- 该 PDF 的 chunk 范围是 `_000` 到 `_037`（共约38个chunk）
- **问题几乎标记了超过 1/3 的文档作为"正确答案"**，等同于没有做真正的 chunk 级答案

**溯源验证（已验证）**：
- ✅ Chunk 溯源链路可行：
  - `meal_snapshot.json` → `data_id: "700e23412eb0"`
  - `config_hashes.chunker: "a67bd087"`
  - Chunk 文件：`data/artifacts/700e23412eb0/chunks_a67bd087/research_reports/2025中国宫颈癌诊疗现状白皮书.jsonl`
  - 可通过 chunk_id 直接定位 chunk 内容

**改进方向（需进一步设计）**：
- 问题生成时应限制 expected_chunks 数量（如最多 3-5 个）
- 或者改用"锚点chunk"策略，只标记最核心的 1-2 个 chunk
- 这需要修改问题生成阶段的 prompt 和后处理逻辑

## 四、改进建议

### 4.1 立即修复（资产包完整性）

| 优先级 | 改进项 | 具体方案 |
|--------|--------|----------|
| P0 | 问题集快照保存 | 确保问题生成后立即写入 `test_sets/{name}.json`，包含完整元数据 |
| P0 | Manifest 修复 | 确保 test_sets 字段正确记录实际使用的问题集 |
| P1 | 实验日志归档 | 将实验过程的 stdout/stderr 日志写入 `experiment.log` |
| P1 | test_set 字段修复 | 正确记录每个问题所属的测试集名称 |

### 4.2 中期改进（数据可信度）

| 优先级 | 改进项 | 具体方案 |
|--------|--------|----------|
| P1 | Hit Rate 异常检测 | 添加阈值告警，如 Hit Rate > 0.95 时发出警告 |
| P1 | FPR 指标修正 | 重新理解 FPR 含义，确保计算逻辑正确（针对无关问题） |
| P2 | **expected_chunks 严格化** | **限制每个问题的 expected_chunks 数量（建议 1-3 个）** |
| P2 | 问题质量审计 | 添加问题-答案相关性检查，防止问题泄露答案 |

### 4.3 长期改进（生产级系统）

| 优先级 | 改进项 | 具体方案 |
|--------|--------|----------|
| P2 | 环境快照 | 使用 `pip freeze` 或 `conda env export` 记录依赖版本 |
| P3 | 执行时间线 | 记录每个阶段的起止时间（数据加载、问题生成、评测等） |
| P3 | 统计显著性检验 | 对多次实验结果进行统计检验，而非仅看单次指标 |

## 六、总结

当前 RAG 评测系统存在**资产包不完整**和**数据可信度存疑**两个核心问题，导致：

1. **无法复现实验**：问题集快照缺失是最严重的问题
2. **指标不可信**：Hit Rate 异常和 FPR 误解使得结果难以采信
3. **Ground Truth 失效**：expected_chunks 覆盖范围过大，等于没有做真正的 chunk 级评估

**已验证无需修改的项目**：
- PDF 相对路径：设计上数据就存放在项目根目录
- Chunk 内容保存：溯源链路已验证可行（data_id + chunker_hash + chunk_id）

建议优先修复 Phase 1 的资产包问题，确保实验结果具备基本的可复现性。
