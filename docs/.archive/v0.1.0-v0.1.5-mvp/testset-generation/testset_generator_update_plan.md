# 问题生成策略系统性分析与重构讨论

## 一、现有两种策略优劣势深度对比

### 1.1 Document-based 策略

#### 优势

| 维度 | 具体表现 |
|------|---------|
| **问题类型多样性** | 6种类型：single_fact、multi_fact、reasoning、comparative、missing、irrelevant |
| **问题真实性** | Prompt 模拟真实用户角色，问题风格口语化、自然 |
| **覆盖全面性** | 能够生成"缺失知识点"和"无关问题"，测试系统的拒答能力 |
| **多跳问题自然性** | LLM 自主决定需要综合哪些信息，而非强制多跳 |

#### 劣势

| 维度 | 具体表现 | 根因分析 |
|------|---------|---------|
| **区块定位准确性** | `_locate_answer_chunks()` 使用关键词匹配，准确率存疑 | 后验推断，LLM 可能"编造"答案中的数据 |
| **Ground Truth 可靠性** | `source_chunks` 字段可能不准确 | 问题生成与区块定位解耦 |
| **文档截断问题** | 固定截断前 8000 字符，长文档后半部分无机会被采样 | 设计缺陷，非技术限制 |
| **验证成本高** | 需要人工抽检或二次 LLM 验证 | 缺乏生成时的约束机制 |

### 1.2 Chunk-based 策略

#### 优势

| 维度 | 具体表现 |
|------|---------|
| **区块定位精确** | `source_chunks` 先验确定，100% 可靠 |
| **评估指标兼容** | 直接可用于 Context Recall/Precision 计算 |
| **可控性强** | 可以精确控制问题的难度和类型 |

#### 劣势

| 维度 | 具体表现 | 根因分析 |
|------|---------|---------|
| **问题风格死板** | Prompt 强调"必须能用提供的文本完全回答"，导致问题偏"考试题"风格 | Prompt 设计过于约束 |
| **多跳问题不自然** | 随机抽取两个不相邻 chunk，可能关联性低，AI 强行生成多跳问题 | 选择逻辑过于机械 |
| **问题类型单一** | 仅 3 种类型：factual、boundary、multi_hop | 缺少 missing、irrelevant 等类型 |
| **无法测试拒答能力** | 所有问题都有答案 | 缺少负面测试用例 |

### 1.3 核心矛盾

```
┌─────────────────────────────────────────────────────────────────┐
│                        核心矛盾                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   Ground Truth 可靠性  ←────────────────→  问题真实性/多样性     │
│         ↑                                    ↑                  │
│         │                                    │                  │
│   Chunk-based                            Doc-based              │
│   (先验约束)                              (后验推断)             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 二、Document-based 策略改进方向探讨

### 2.1 增强区块判定精确性

#### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A. 关键词匹配优化** | 改进 `_locate_answer_chunks()` 算法 | 改动小 | 本质仍是后验推断，上限有限 |
| **B. 要求 LLM 输出原文引用** | Prompt 要求输出 verbatim quote，用引用定位 chunk | 可验证性强 | 增加 token 消耗 |
| **C. 先选 chunk，再生成问题** | 融合 Chunk-based 的选择逻辑 | Ground truth 先验确定 | 需要重新设计 prompt |
| **D. 混合策略** | 不同问题类型采用不同策略 | 灵活 | 实现复杂度高 |

#### 推荐：方案 C + B 组合

```
选择 chunks → 喂给 LLM → 要求输出原文引用 → 验证引用确实来自选定的 chunks
```

### 2.2 文档处理机制优化

#### 当前问题

```python
DOCUMENT_TRUNCATE_MAX = 8000  # 固定截断前 8000 字符

# 问题：
# 1. 长文档后半部分永远无机会被采样
# 2. 8000 字符可能不够 LLM 理解上下文
# 3. 截断点可能恰好切断重要信息
```

#### 改进方案：分段随机抽样

```
┌─────────────────────────────────────────────────────────────────┐
│                    分段随机抽样策略                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   长文档 (如 50000 字符)                                         │
│   ├── 段落 1: [0, 10000)                                        │
│   ├── 段落 2: [10000, 20000)                                    │
│   ├── 段落 3: [20000, 30000)                                    │
│   ├── 段落 4: [30000, 40000)                                    │
│   └── 段落 5: [40000, 50000]                                    │
│                                                                 │
│   抽样策略：                                                      │
│   - 单段抽样：随机选 1 个段落，生成 single_fact 问题               │
│   - 双段抽样：随机选 2 个段落（可相邻/不相邻），生成多跳问题         │
│   - 全文档抽样：随机选多个段落拼接，生成综合问题                    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 抽样参数设计

| 参数 | 建议值 | 说明 |
|------|--------|------|
| 单段长度 | 4000-8000 字符 | 足够 LLM 理解上下文 |
| 段落划分方式 | 按字符数均匀划分 或 按文档结构（章节）划分 | 后者更语义化 |
| 抽样概率 | 各段落等概率 | 确保长文档各部分都有机会 |
| 多段组合 | 支持相邻段 + 不相邻段 | 覆盖不同问题类型 |

#### 与 Chunk 的关系

**关键问题**：抽样段落与 Chunk 的映射关系

```
抽样段落 (4000-8000 字符) → 包含多个 Chunk (每个约 500-1000 字符)
```

**建议**：
1. 抽样时记录段落对应的 chunk ID 列表
2. LLM 生成问题时，要求输出引用的原文
3. 用原文引用反向定位到具体 chunk
4. 由于原文引用来自抽样段落，定位必然准确

### 2.3 当前抽样机制状态

根据代码分析，当前**未实施**分段随机抽样，仅使用固定截断：

```python
# 当前实现 (test_generator.py:1377-1382)
doc_key = str(hash(document_content[:1000]))
if doc_key in self._doc_truncate_cache:
    truncated_doc = self._doc_truncate_cache[doc_key]
else:
    truncated_doc = document_content[: self.DOCUMENT_TRUNCATE_MAX]  # 固定截断
```

## 三、问题生成过程中的依据追踪机制

### 3.1 两种追踪方式对比

| 维度 | 实时标注（生成时） | 后验推断（事后匹配） |
|------|-------------------|-------------------|
| **准确性** | ✅ 高：LLM 明确知道依据 | ❌ 低：关键词可能匹配多个位置 |
| **可验证性** | ✅ 高：原文引用可直接验证 | ❌ 低：无法验证是否真的来自该位置 |
| **Token 消耗** | ⚠️ 增加：需要输出引用 | ✅ 无额外消耗 |
| **实现复杂度** | ⚠️ 中：需要设计 prompt | ✅ 低：现有实现 |
| **幻觉检测** | ✅ 可检测：引用不存在则说明幻觉 | ❌ 无法检测 |

### 3.2 实时标注方案设计

#### Prompt 改进

```python
EVIDENCE_AWARE_PROMPT = """你是一位金融行业从业者。以下是文档的选段：

## 文档选段
{selected_segments}

## 任务
请基于这些选段，生成一个【{question_type}】类型的问题。

## 关键要求
1. **依据追踪**：你必须明确指出答案的依据来自哪个选段的哪些内容
2. **原文引用**：答案中必须包含原文引用，用【】标注
3. **问题风格**：口语化、真实，像在问同事问题

## 输出格式（严格 JSON）
{{
    "question": "你的问题",
    "answer": "答案，包含【原文引用】",
    "evidence": [
        {{
            "segment_index": 0,  // 来自第几个选段
            "quote": "原文引用内容",  // 必须与选段原文完全一致
            "relevance": "该引用如何支撑答案"
        }}
    ],
    "difficulty": "easy/medium/hard"
}}
"""
```

#### 验证流程

```
┌─────────────────────────────────────────────────────────────────┐
│                    依据追踪验证流程                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   1. LLM 输出 evidence.quote                                    │
│                    ↓                                            │
│   2. 验证 quote 是否存在于选定的选段中                             │
│      ├── 存在 → Ground Truth 可靠                               │
│      └── 不存在 → LLM 幻觉，标记为无效问题                        │
│                    ↓                                            │
│   3. 用 quote 定位到具体 chunk                                   │
│      （选段已记录对应的 chunk ID 列表）                           │
│                    ↓                                            │
│   4. source_chunks = 定位到的 chunk ID 列表                      │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 准确性差异分析

#### 场景 1：数据类问题

```
问题："2024年光模块市场规模多少？"
答案："2024年光模块市场规模为【150亿元】，同比增长20%。"
```

| 方式 | 结果 | 准确性 |
|------|------|--------|
| 实时标注 | `evidence.quote = "2024年光模块市场规模为150亿元"` | ✅ 可验证 |
| 后验推断 | 关键词 "150亿元" 可能匹配多个 chunk | ❌ 可能错误 |

#### 场景 2：推理类问题

```
问题："为什么CPO能降低功耗？"
答案："CPO通过【缩短光引擎与交换芯片的距离】来降低功耗，因为【信号传输距离越短，损耗越小】。"
```

| 方式 | 结果 | 准确性 |
|------|------|--------|
| 实时标注 | 两个引用分别来自不同选段 | ✅ 可验证多跳 |
| 后验推断 | 关键词分散，难以准确匹配 | ❌ 高概率错误 |

#### 场景 3：幻觉检测

```
问题："光模块行业的ESG评级如何？"
答案："光模块行业ESG评级为【A级】。"（实际文档未提及ESG）
```

| 方式 | 结果 | 准确性 |
|------|------|--------|
| 实时标注 | 验证时发现 quote 不存在于选段 → 标记为幻觉 | ✅ 可检测 |
| 后验推断 | 关键词匹配失败，返回空列表 | ⚠️ 无法区分幻觉与匹配失败 |

## 四、策略重构整体方案

### 4.1 设计原则

1. **Ground Truth 先验确定**：问题生成前先确定依据的文档范围
2. **依据可追溯**：生成时要求输出原文引用
3. **问题风格真实**：保留 Doc-based 的角色扮演 prompt
4. **覆盖全面**：支持多种问题类型
5. **幻觉可检测**：验证引用是否真实存在

### 4.2 重构方案：融合策略

```
┌─────────────────────────────────────────────────────────────────┐
│                    融合策略架构                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   ┌──────────────┐                                              │
│   │ 1. 文档分段   │  按字符数或结构划分为多个选段                  │
│   └──────┬───────┘                                              │
│          ↓                                                      │
│   ┌──────────────┐                                              │
│   │ 2. 选段抽样   │  根据问题类型选择 1-2 个选段                   │
│   │              │  - single_fact: 1 段                          │
│   │              │  - multi_fact/reasoning: 2 段（可不相邻）      │
│   │              │  - comparative: 2 段                          │
│   │              │  - missing: 全文档抽样                         │
│   │              │  - irrelevant: 不依赖文档                      │
│   └──────┬───────┘                                              │
│          ↓                                                      │
│   ┌──────────────┐                                              │
│   │ 3. Chunk映射 │  记录选段对应的 chunk ID 列表                  │
│   └──────┬───────┘                                              │
│          ↓                                                      │
│   ┌──────────────┐                                              │
│   │ 4. 问题生成   │  喂给 LLM，要求输出原文引用                    │
│   │              │  Prompt 保留真实用户风格                       │
│   └──────┬───────┘                                              │
│          ↓                                                      │
│   ┌──────────────┐                                              │
│   │ 5. 引用验证   │  验证 quote 是否存在于选段                    │
│   │              │  - 存在 → Ground Truth 可靠                   │
│   │              │  - 不存在 → 标记为无效，重新生成                │
│   └──────┬───────┘                                              │
│          ↓                                                      │
│   ┌──────────────┐                                              │
│   │ 6. Chunk定位 │  用 quote 定位到具体 chunk                    │
│   └──────────────┘                                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.3 问题类型与选段策略映射

| 问题类型 | 选段策略 | Ground Truth 来源 | 特殊处理 |
|---------|---------|------------------|---------|
| single_fact | 随机 1 段 | 选段对应的 chunks | 无 |
| multi_fact | 随机 2 段（可不相邻） | 两段对应的 chunks | 验证引用来自两段 |
| reasoning | 随机 2 段（可不相邻） | 两段对应的 chunks | 要求输出推理依据 |
| comparative | 随机 2 段 | 两段对应的 chunks | 确保两段有可对比内容 |
| missing | 全文档抽样 | 空（预期无答案） | 验证答案确实说"文档未提及" |
| irrelevant | 不依赖文档 | 空 | 验证答案确实说"与文档无关" |

### 4.4 多跳问题合理性保障

#### 当前 Chunk-based 的问题

```python
# 当前实现：机械选择间隔 2-5 个 chunk 的组合
for i in range(len(chunks)):
    for j in range(i + 2, min(i + 5, len(chunks))):
        groups.append([chunks[i], chunks[j]])
```

**问题**：两个 chunk 可能毫无关联，LLM 强行生成多跳问题导致不自然。

#### 改进方案：语义相关性预筛选

```
┌─────────────────────────────────────────────────────────────────┐
│              多跳问题选段策略                                     │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   方案 A：基于文档结构                                            │
│   - 优先选择同一章节内的不同段落                                   │
│   - 或选择有交叉引用的段落                                         │
│                                                                 │
│   方案 B：基于关键词共现                                          │
│   - 预先提取各选段的关键词                                         │
│   - 选择有共同关键词的选段组合                                     │
│   - 确保两段有语义关联                                            │
│                                                                 │
│   方案 C：基于 LLM 预判断                                         │
│   - 先让 LLM 判断两个选段是否适合生成多跳问题                       │
│   - 只保留适合的组合                                              │
│                                                                 │
│   方案 D：让 LLM 自主决定                                         │
│   - 给 LLM 多个选段（如 3-4 段）                                   │
│   - 让 LLM 自主选择哪些选段适合组合                                │
│   - 输出 evidence 时指明使用了哪些选段                             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**推荐**：方案 D（让 LLM 自主决定）

理由：
- LLM 比规则更能判断语义关联
- 减少预筛选的计算成本
- 生成的问题更自然

### 4.5 预期效果

| 维度 | 改进前 | 改进后 |
|------|-------------------|-------------------|
| **Ground Truth 准确率** | ~70%（估算） | ~95%+ |
| **问题真实性** | ✅ 高 | ✅ 高（保留） |
| **问题类型覆盖** | 6 种 | 6 种（保留） |
| **多跳问题合理性** | ⚠️ 中等 | ✅ 高（LLM 自主决定） |
| **幻觉检测能力** | ❌ 无 | ✅ 有（引用验证） |
| **长文档覆盖率** | ❌ 低（仅前 8000 字符） | ✅ 高（随机抽样） |

## 六、总结

本次讨论形成的核心结论：

1. **融合策略是最佳方向**：结合 Chunk-based 的精确性和 Doc-based 的真实性

2. **分段随机抽样解决覆盖问题**：长文档各部分都有机会被采样

3. **实时标注优于后验推断**：原文引用机制确保 Ground Truth 可靠

4. **LLM 自主决定多跳组合**：比机械规则更合理

5. **幻觉可检测**：引用验证机制可识别无效问题
