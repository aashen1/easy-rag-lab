# 文档级问题生成策略设计

## 1. 现有问题生成策略分析

### 1.1 现有策略概述

当前系统（[src/test_generator.py](file:///b:/project/ash-easy-rag/src/test_generator.py)）实现了三种问题生成策略：

| 策略 | 描述 | 输入 | 难度 |
|------|------|------|------|
| `factual` | 基于单个 chunk 生成事实性问题 | 单个 chunk | easy |
| `boundary` | 基于相邻 chunk 生成边界问题 | 两个相邻 chunk | medium |
| `multi_hop` | 基于非相邻 chunk 生成多跳问题 | 两个非相邻 chunk | hard |

### 1.2 现有策略的问题

#### 1.2.1 基于 Chunk 的局限性

**问题**：问题生成基于 chunk 而非完整文档，导致：

1. **上下文缺失**：chunk 切分可能切断关键信息的关联
2. **问题片面**：无法生成需要全局视角的问题
3. **信息孤岛**：难以测试跨文档的综合分析能力

#### 1.2.2 问题类型单一

**问题**：只有三种策略，无法覆盖真实用户场景：

| 缺失场景 | 描述 |
|----------|------|
| 缺失知识点 | 用户询问文档中不存在的信息 |
| 无关问题 | 用户询问与文档主题无关的问题 |
| 对比分析 | 需要对比多个实体/指标的问题 |
| 推理型问题 | 需要逻辑推理才能回答的问题 |

#### 1.2.3 问题不够真实

**问题**：生成的问题像考试题，不像真实用户会问的问题。

**示例分析**：

```
现有问题（不真实）：
"根据提供的文档片段，分析科瑞技术、普源精电和猎奇智能在光模块产业链中的定位和技术优势..."

真实用户问题：
"科瑞技术在光模块领域主要做什么？和普源精电比有什么区别？"
```

**问题特征**：
- 使用"根据文档/片段"等学术化表述
- 问题过于正式、结构化
- 缺乏口语化表达
- 不符合金融从业者的实际提问习惯

### 1.3 现有提示词模板分析

以 `FACTUAL_PROMPT` 为例：

```python
FACTUAL_PROMPT = """你是一个金融研报问答系统的测试工程师。请根据以下文本片段，生成一个可以用该文本直接回答的事实性问题。

要求：
1. 问题必须能用提供的文本完全回答
2. 问题应该具体、明确，避免过于宽泛
3. 答案应该简洁准确，直接引用文本中的关键数据或结论

```

**问题**：
1. 角色设定为"测试工程师"，导致问题像测试用例
2. 强调"直接回答"，限制了问题的多样性
3. 没有引导生成真实用户场景的问题
4. 缺少对问题风格的约束

## 2. 新的问题类型定义

### 2.1 设计原则

1. **真实性**：问题应模拟真实金融从业者的提问方式
2. **多样性**：覆盖不同场景、不同难度的问题类型
3. **可评估性**：每种类型有明确的评估标准
4. **边界覆盖**：包含正向、负向、边界场景

### 2.2 问题类型定义

#### Type 1: 单知识点查询 (Single Fact Query)

**定义**：查询文档中某个具体事实或数据点的问题。

**特征**：
- 问题简短、直接
- 答案明确、单一
- 不需要推理或综合

**真实场景示例**：

| 场景 | 问题示例 |
|------|----------|
| 查数据 | "2024年光模块市场规模大概多少？" |
| 查公司 | "科瑞技术是做什么的？" |
| 查技术 | "CPO技术的主要优势是什么？" |
| 查参数 | "1.6T光模块的功耗大概是多少？" |

**生成要求**：
- 问题口语化，避免学术化表述
- 答案应直接来自文档，无需推理
- 难度标记为 `easy`

#### Type 2: 多知识点综合 (Multi-Fact Synthesis)

**定义**：需要综合文档中多个相关信息才能回答的问题。

**特征**：
- 需要整合多个数据点或结论
- 可能涉及对比、归纳、总结
- 答案需要组织多个信息片段

**真实场景示例**：

| 场景 | 问题示例 |
|------|----------|
| 对比公司 | "科瑞技术和猎奇智能在光模块设备上有什么区别？" |
| 总结趋势 | "光模块行业未来几年的增长趋势怎么样？" |
| 综合分析 | "为什么说CPO技术是未来的发展方向？" |
| 横向比较 | "800G和1.6T光模块在技术难度上差多少？" |

**生成要求**：
- 问题应体现真实业务需求
- 答案需要明确指出信息来源
- 难度标记为 `medium`

#### Type 3: 推理型问题 (Reasoning Required)

**定义**：需要基于文档信息进行逻辑推理才能回答的问题。

**特征**：
- 文档中没有直接答案
- 需要理解因果关系
- 可能涉及预测或判断

**真实场景示例**：

| 场景 | 问题示例 |
|------|----------|
| 原因分析 | "为什么CPO能降低功耗？" |
| 影响判断 | "如果800G需求翻倍，对设备商有什么影响？" |
| 趋势预测 | "按现在的增速，2026年市场规模能达到多少？" |
| 优劣判断 | "硅光方案和传统方案哪个更有前景？" |

**生成要求**：
- 推理依据必须来自文档
- 答案需要展示推理过程
- 难度标记为 `hard`

#### Type 4: 对比分析 (Comparative Analysis)

**定义**：需要对比两个或多个实体/指标/方案的问题。

**特征**：
- 明确的对比对象
- 需要多维度比较
- 可能需要得出结论

**真实场景示例**：

| 场景 | 问题示例 |
|------|----------|
| 公司对比 | "中际旭创和新易盛这两家公司哪个更值得投资？" |
| 技术对比 | "CPO和LPO两种技术路线各有什么优缺点？" |
| 指标对比 | "2024年和2023年的市场规模增长了多少？" |
| 方案对比 | "可插拔模块和共封装方案的成本差异大吗？" |

**生成要求**：
- 对比对象应在文档中均有提及
- 答案需要客观呈现对比结果
- 难度标记为 `medium` 或 `hard`

#### Type 5: 缺失知识点 (Missing Knowledge)

**定义**：用户询问文档中不存在或不完整的信息。

**特征**：
- 文档无法完全回答
- 测试系统的"不知道"能力
- 可能部分可回答

**真实场景示例**：

| 场景 | 问题示例 |
|------|----------|
| 完全缺失 | "光模块行业的ESG评级情况怎么样？" |
| 部分缺失 | "2025年的市场预测数据有吗？"（文档只有到2024年） |
| 细节缺失 | "科瑞技术的具体客户名单有哪些？" |
| 跨领域 | "光模块和AI芯片的发展有什么关系？"（文档未涉及） |

**生成要求**：
- 问题应合理，不能过于离谱
- 答案应明确指出"文档未提及"或"信息不完整"
- 难度标记为 `special`

#### Type 6: 无关问题 (Irrelevant Question)

**定义**：与文档主题完全无关的问题。

**特征**：
- 测试系统的拒答能力
- 问题本身合理，但与文档无关
- 可能涉及其他领域

**真实场景示例**：

| 场景 | 问题示例 |
|------|----------|
| 其他行业 | "新能源汽车的电池技术发展怎么样？" |
| 其他主题 | "最近美联储加息对股市有什么影响？" |
| 完全无关 | "推荐几家好吃的餐厅？" |

**生成要求**：
- 问题应合理，体现真实用户可能误问的场景
- 答案应为"该问题与文档内容无关"
- 难度标记为 `special`

### 2.3 问题类型分布建议

| 类型 | 占比 | 说明 |
|------|------|------|
| 单知识点查询 | 30% | 最常见的用户查询 |
| 多知识点综合 | 25% | 中等复杂度的分析需求 |
| 推理型问题 | 15% | 高级用户的深度需求 |
| 对比分析 | 15% | 投资决策支持需求 |
| 缺失知识点 | 10% | 测试边界处理能力 |
| 无关问题 | 5% | 测试拒答能力 |

## 4. 问题难度和真实性评估机制设计

### 4.1 难度评估机制

#### 4.1.1 难度维度定义

| 维度 | 权重 | 评估标准 |
|------|------|----------|
| 信息跨度 | 30% | 需要查阅的文档范围（单段落/多段落/全文） |
| 推理深度 | 30% | 是否需要推理，推理的复杂度 |
| 答案复杂度 | 20% | 答案是单一事实/需要组织/需要判断 |
| 领域知识 | 20% | 是否需要外部领域知识 |

#### 4.1.2 难度计算规则

```python
def calculate_difficulty(question_data: dict) -> str:
    score = 0

    # 信息跨度评分
    sources = question_data.get("answer_sources", [])
    if len(sources) == 1:
        score += 1
    elif len(sources) <= 3:
        score += 2
    else:
        score += 3

    # 推理深度评分
    question_type = question_data.get("question_type", "")
    if question_type == "单知识点查询":
        score += 1
    elif question_type in ["多知识点综合", "对比分析"]:
        score += 2
    elif question_type == "推理型问题":
        score += 3
    else:
        score += 1

    # 答案复杂度评分
    answer = question_data.get("answer", "")
    if len(answer) < 50:
        score += 1
    elif len(answer) < 200:
        score += 2
    else:
        score += 3

    # 领域知识评分（需要外部知识的问题更难）
    if question_type == "缺失知识点":
        score += 2
    else:
        score += 1

    # 映射到难度等级
    if score <= 4:
        return "easy"
    elif score <= 6:
        return "medium"
    else:
        return "hard"
```

### 4.2 真实性评估机制

#### 4.2.1 真实性维度定义

| 维度 | 权重 | 评估标准 |
|------|------|----------|
| 口语化程度 | 25% | 是否像真实用户会说的话 |
| 业务相关性 | 25% | 是否体现真实业务场景 |
| 问题合理性 | 25% | 问题是否有意义、有意图 |
| 风格自然度 | 25% | 是否避免学术化、模板化表述 |

```python
def check_authenticity_rules(question: str) -> dict:
    issues = []

    # 检测学术化表述
    academic_patterns = [
        "根据文档",
        "根据提供的信息",
        "请分析",
        "请说明",
        "请对比",
        "请总结",
        "文档中提到",
        "片段中提到",
    ]
    for pattern in academic_patterns:
        if pattern in question:
            issues.append(f"包含学术化表述：'{pattern}'")

    # 检测模板化开头
    template_starts = [
        "请问",
        "请解释",
        "请描述",
    ]
    for start in template_starts:
        if question.startswith(start):
            issues.append(f"模板化开头：'{start}'")

    # 检测问题长度（过长可能过于复杂）
    if len(question) > 100:
        issues.append("问题过长，可能不够直接")

    return {
        "has_issues": len(issues) > 0,
        "issues": issues,
        "is_authentic": len(issues) == 0
    }
```
