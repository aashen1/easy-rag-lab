## 第一部分：冒烟验收计划

### 验收策略

分三层验收，从快到慢：

| 层级 | 内容 | 预计耗时 | 目标 |
|------|------|----------|------|
| L1: lint + 单元测试 | `pixi run lint` + `pixi run test` | ~1 min | 确认代码质量和已有测试不回归 |
| L2: 补充缺失测试 | 为 `clone_for_concurrency()`、`VectorIndexer.reopen()`/`is_closed()` 补单元测试 | ~10 min | 填补测试覆盖缺口 |
| L3: 端到端冒烟 | `pixi run experiment --config exp_configs/smoke_tests/smoke_quick.yaml` | ~3-5 min | 真实链路验证 |

### L1: lint + 单元测试

```bash
pixi run lint
pixi run test
```

- 如果有失败 → 修复后再继续
- 预期：全绿（当前 ~1089 个单元测试）

### L2: 补充缺失测试

根据调查，以下功能缺少专门测试：

#### 2.1 `RAGPipeline.clone_for_concurrency()` — 无单元测试

文件：`tests/test_pipeline.py`

需测试的场景：
- clone 后共享 indexer/embedder/token_tracker（同一对象引用）
- clone 后 generator 是新实例（不同对象）
- clone 后 reranker/query_rewriter 为 None（不继承）
- clone 后的 pipeline 能正常 query（mock 全链路）
- clone 后的 pipeline close() 不关闭共享 indexer

#### 2.2 `VectorIndexer.reopen()` / `is_closed()` — 无单元测试

文件：`tests/test_indexer.py`

需测试的场景：
- `close()` 后 `is_closed()` 返回 True
- 初始状态 `is_closed()` 返回 False
- `reopen()` 后 `is_closed()` 返回 False，client 可用
- `reopen()` 在未关闭状态下是 no-op
- `reopen()` 重新创建 QdrantClient（验证构造参数）

## 第三部分：下版本（v0.1.16）推进方向建议

基于当前项目状态和 v0.2.0 路线图，建议 v0.1.16 聚焦以下方向（选 1-2 个）：

### 方向 A：透明版完整实验报告（FEAT-010）— 原计划 v0.1.15 内容

- 当前实验报告是 JSON/CSV，非技术人员无法阅读
- 目标：生成 Markdown/HTML 格式的可读报告，含图表、指标对比、结论
- 价值：让实验结果"看得见"，为 v0.2.0 开源做准备
- 依赖：无阻塞，可直接推进

### 方向 B：Baseline 标定与"花头"效果验证

- 当前缺乏可信 baseline，无法判断各种"花头"（HyDE、Multi-Query、Reranker 等）是否真的有效
- 目标：用 smoke_full.yaml 跑一轮完整实验，标定各配置的指标基线，验证花头效果
- 价值：回答"这些功能到底有没有用"的根本问题
- 依赖：需要 API 额度和时间

### 方向 C：RAGAS 深度核实

- 当前 RAGAS 评测链路基本可用但未充分验证
- 目标：五大指标（faithfulness, answer_relevancy, context_precision, context_recall, answer_correctness）逐一验收，确认数值可信
- 价值：v0.2.0 的前置条件
- 依赖：需要 RAGAS 环境和 API 额度

### 方向 D：dev → main 合并准备

- dev 分支已领先 main 50+ commit，长期不合并会增加冲突风险
- 目标：清理 dev 分支的临时文件、确认文档一致性、准备 dev → main 的合并
- 价值：为 v0.2.0 开源发布做准备
- 依赖：无

### 推荐优先级

**A > B > D > C**

理由：
- A（实验报告）是 v0.1.15 原计划内容，且是"看得见"的交付，用户可感知
- B（baseline 标定）依赖 A 的报告输出，先有报告才能看结果
- D（合并准备）是 v0.2.0 的前置，但不急
- C（RAGAS 核实）重要但不紧急，且需要较多 API 资源
