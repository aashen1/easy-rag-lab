## 一、背景与目标

### 1.1 问题背景

项目当前存在 **59 个 markdown 文件**，分布在 **7+ 个目录**中，存在以下核心问题：

| 问题类型 | 具体表现 | 影响 |
|---------|---------|------|
| **分类混乱** | 开发手记、故障排查、技术决策、代码审查混放 | 难以定位所需文档 |
| **严重重叠** | Meal 系统 3 份文档、测试体系 6 份文档、幽灵文件夹 3 份文档存在大量重复 | 信息冗余、维护困难 |
| **版本失配** | 部分文档与当前代码不一致（如 README 项目结构过时） | 误导读者 |
| **缺少索引** | 无全局导航，新开发者难以快速定位 | 学习成本高 |
| **命名不一致** | 中英文混用（如 `chat-幽灵文件夹排查指南.md`） | 不专业、不便于检索 |
| **缺少版本演进记录** | 无"年轮"式文档追踪版本迭代历程 | 难以追溯决策背景 |
| **待做事项分散** | code-review 中的"建议单开"内容容易被遗忘 | 项目"卫生情况"难以追踪 |
| **聊天记录入库无规范** | 网页端聊天导出的文档命名和格式不规范 | 文档质量参差不齐 |

### 1.2 核心理念：AI 时代的文档观

基于用户在 `notes/chat-AI时代的新Git规范.md` 中阐述的理念：

1. **文档是意图源码，代码是编译产物**
   - 在 AI 辅助开发中，Spec/Roadmap/决策文档是"给 AI 编译的意图"
   - 文档的重要性应高于传统实践

2. **"抛接球"式版本演进**
   - 抛球：创建版本 Spec/Feature Plan（意图）
   - 接球：AI 生成代码，人工验收
   - 复盘：生成 outcome 文档（承诺 vs 交付 vs 调整）
   - 归档：形成项目"年轮"

3. **版本演进文档套件**
   - 每次发版后：Code Review → 打扫卫生（bugfix/refactor）→ 拟定下版本方向
   - 这些文档形成项目的"生长日记"

### 1.3 重构目标

1. **清晰的结构**：每种文档类型有明确的存放位置
2. **单一信源**：同一信息只在一处维护，避免重复
3. **版本演进可追溯**：建立"年轮"式文档体系
4. **双向友好**：人类易于阅读导航，AI 易于理解上下文
5. **轻量维护**：简化文档生命周期管理，降低维护成本

#### 2.3.2 `docs/reviews/` — 版本验收报告

按版本组织，每个版本目录包含：

| 文档 | 用途 |
|------|------|
| `code-review.md` | 发版后的全面代码审查，分析实现质量、发现 bug、提出重构建议 |
| `outcome.md` | 承诺 vs 交付对照表，记录哪些实现了、哪些降级了、哪些延期了 |
| `next-direction.md` | 下版本的开发大方向、主要 feature、注意事项 |

这对应了用户描述的发版后流程：
1. 让 AI 做全面 code review → `code-review.md`
2. 打扫卫生，落实 bug 和重构建议 → 更新 `outcome.md`
3. 拟定下版本开发大方向 → `next-direction.md`

## 三、CHANGELOG 规范调整

### 3.1 当前问题

当前 CHANGELOG.md 存在以下问题：
1. **内容过载**：过于详细，不好读
2. **混入非变更内容**：Known Issues、Next Steps 不应放在 CHANGELOG
3. **格式不够精简**：每个功能点都展开详细描述

### 3.2 CHANGELOG 应该是什么

根据 [Keep a Changelog](https://keepachangelog.com/) 规范：

> A changelog is a file which contains a curated, chronologically ordered list of notable changes for each version of an open source project.

**CHANGELOG 应该是**：
- 变更日志，记录每个版本的**显著变更**
- 简洁、易于阅读
- 面向用户，而非开发者

**CHANGELOG 不应该是**：
- Issue 追踪器
- Roadmap
- 详细的功能文档
- Known Issues 列表

### 3.3 调整方案

1. **精简 CHANGELOG.md**
   - 每个版本只保留高层摘要
   - 详细内容移到 `docs/version-history.md` 或对应功能文档

2. **移除 Known Issues 和 Next Steps**
   - Known Issues → 放到 `docs/troubleshooting/` 或 GitHub Issues
   - Next Steps → 放到 `TODO.md` 或 `docs/reviews/vX.X.X/next-direction.md`

3. **示例精简格式**

```markdown
# Changelog

## [Unreleased]

### Added
- Sampling System with three modes (count/pages/ratio)
- Meal Data Management System
- Test Set Generator
- Experiment System with multi-variant comparison
- Token Tracking System

### Changed
- Sampling now applies end-to-end across all pipeline stages

### Fixed
- Fix Generator to use Anthropic API `system` parameter

## [0.1.0] - 2026-04-16

### Added
- Core RAG pipeline (PDF parsing → chunking → embedding → indexing → retrieval → generation)
- Evaluation metrics (Hit Rate, MRR, NDCG)
- Multi-LLM preset support

[详细功能说明请参阅 docs/guides/ 或 docs/version-history.md]
```

## 四、文档分类标准

### 4.1 文档类型与存放位置

| 类型 | 存放位置 | 命名格式 | 用途 |
|------|---------|---------|------|
| **版本演进年轮** | `docs/version-history.md` | 固定名称 | 记录版本迭代历程 |
| **待做事项总表** | `docs/backlog.md` | 固定名称 | 项目"卫生情况"总入口，追踪所有待做事项 |
| **版本验收报告** | `docs/reviews/vX.X.X/` | 按版本组织 | 代码审查、outcome、下版本方向 |
| **快速上手** | `docs/getting-started.md` | 固定名称 | 5 分钟内让新用户跑通系统 |
| **系统架构** | `docs/architecture.md` | 固定名称 | 描述系统整体架构、模块关系 |
| **CLI 参考** | `docs/cli-reference.md` | 固定名称 | 所有 CLI 命令的完整参考 |
| **配置参考** | `docs/config-reference.md` | 固定名称 | config.yaml 所有配置节说明 |
| **使用指南** | `docs/guides/` | `<功能>.md` | 功能使用指南 |
| **故障排查** | `docs/troubleshooting/` | `<问题描述>.md` | 已解决故障的排查记录 |
| **历史归档** | `docs/archive/` | `<类型>-<主题>.md` | 只读历史文档、精简后的聊天记录 |

### 4.2 状态标签规范

每个文档头部包含简化状态标签：

```markdown
<!-- status: active | archived | deprecated -->
```

- `active`：当前有效，需随代码更新（默认状态，可省略）
- `archived`：历史参考，不再主动维护
- `deprecated`：已被其他文档替代，保留仅供溯源

### 4.3 何时不创建文档

| 场景 | 替代方案 |
|------|---------|
| 代码注释能说明的问题 | 直接写在代码里 |
| API 变更 | 更新 `CHANGELOG.md` |
| 临时想法/TODO | 添加到 `docs/backlog.md` |
| AI 对话原始记录 | 精简后入库，或直接删除 |

## 八、长期维护机制

### 8.1 文档更新触发条件

| 代码变更类型 | 需更新的文档 |
|-------------|-------------|
| CLI 参数变更 | `docs/cli-reference.md` |
| config.yaml 结构变更 | `docs/config-reference.md` |
| 新增/删除模块 | `docs/architecture.md` |
| 新增功能 | 对应 `docs/guides/*.md` |
| Bug 修复 | `docs/troubleshooting/` 中的排障记录 |
| 版本发布 | `docs/version-history.md` + `docs/reviews/vX.X.X/` |

### 8.2 版本发布流程

1. **发版前**：检查所有 active 文档与代码的一致性
2. **发版后**：
   - 创建 `docs/reviews/vX.X.X/code-review.md`（代码审查）
   - 打扫卫生，修复 bug 和重构
   - 创建 `docs/reviews/vX.X.X/outcome.md`（交付对照）
   - 拟定下版本方向，创建 `docs/reviews/vX.X.X/next-direction.md`
   - 更新 `docs/version-history.md`
3. **归档**：将已完成的 spec 归档到 `docs/archive/specs/`

### 8.3 AI 协作规范

在 CLAUDE.md 中加入以下规则：

```markdown
### 文档维护规则

- 创建新功能时，同步创建 `docs/guides/<feature>.md`
- 修复疑难 bug 时，创建 `docs/troubleshooting/<bug-name>.md`
- 版本发布后，创建 `docs/reviews/vX.X.X/` 目录下的验收报告
- 代码变更必须同步更新相关文档
- 文档文件名统一使用英文
- code-review 中"建议单开"的内容必须同时添加到 `docs/backlog.md`
- 聊天记录入库前必须精简内容、规范命名
```

## 九、聊天记录入库流程

### 9.1 问题背景

用户会在网页端与 AI 聊天，聊到一些好的点子时会导出对话，存入项目目录。这些文档存在以下问题：
- 文件名不规范（如 `chat-中文标题.md`）
- 内容冗长，包含大量对话过程
- 缺乏元数据，难以追溯来源和关联

### 9.2 入库流程

当有新的聊天记录需要入库时，按以下流程处理：

#### Step 1：评估价值

| 价值类型 | 处理方式 |
|---------|---------|
| **核心 idea**：提出了有价值的设计思路或解决方案 | 入库，精简后归档 |
| **决策记录**：记录了重要技术决策的讨论过程 | 入库，提炼决策要点 |
| **排障经验**：解决了某个疑难问题 | 入库，提炼为 troubleshooting 文档 |
| **临时讨论**：无长期参考价值 | 不入库，直接删除 |

#### Step 2：精简内容

入库前必须精简内容，只保留核心信息：

```markdown
# <主题>

<!-- status: active | archived -->

> 来源：网页端聊天记录
> 日期：YYYY-MM-DD
> 关联：[feature/bugfix/refactor ID](backlog.md#ID)

## 核心观点

<3-5 句话概括核心 idea>

## 详细内容

<精简后的详细说明，去除对话过程>

## 决策要点

- 决策 1：...
- 决策 2：...

## 待办事项

- [ ] 待办 1
- [ ] 待办 2

---

*原文档：`chat-原始标题.md`（已删除）*
```

#### Step 3：规范命名

文件名规范：
- 使用英文，小写，连字符分隔
- 格式：`<类型>-<主题>.md`
- 类型：`idea`、`decision`、`troubleshooting`

示例：
- `idea-ai-era-git-practice.md`（AI 时代 Git 规范讨论）
- `decision-rag-mvp-choices.md`（RAG MVP 技术选型决策）
- `troubleshooting-ghost-folder.md`（幽灵文件夹排查经验）

#### Step 4：放入合适目录

| 内容类型 | 存放位置 |
|---------|---------|
| 设计思路/idea | `docs/archive/` |
| 技术决策 | `docs/reviews/vX.X.X/` 或 `docs/archive/` |
| 排障经验 | `docs/troubleshooting/` |

#### Step 5：更新关联文档

- 如有待办事项，添加到 `docs/backlog.md`
- 如关联某个 feature/bugfix，在对应文档中添加引用

### 9.3 入库检查清单

```markdown
- [ ] 评估文档价值，决定是否入库
- [ ] 精简内容，只保留核心信息
- [ ] 规范文件名（英文、小写、连字符）
- [ ] 添加元数据（来源、日期、关联）
- [ ] 放入合适目录
- [ ] 更新 backlog.md（如有待办事项）
- [ ] 删除原始聊天记录
```

### 9.4 示例：`chat-AI时代的新Git规范.md` 入库

**原始文件**：`notes/chat-AI时代的新Git规范.md`

**入库处理**：
1. 评估价值：提出了 AI 时代的文档观，有长期参考价值
2. 精简内容：提炼核心观点，去除对话过程
3. 规范命名：`idea-ai-era-git-practice.md`
4. 放入目录：`docs/archive/`
5. 更新关联：在本文档中引用其核心理念

**入库后文件**：`docs/archive/idea-ai-era-git-practice.md`

## 十一、风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| 迁移过程中链接失效 | 迁移前扫描所有文档中的内部链接，迁移后统一更新 |
| 合并文档时信息丢失 | 合并前先备份，保留所有原文档至归档目录 |
| 团队成员不熟悉新结构 | 在 CLAUDE.md 和 README 中明确文档规范 |
| 文档更新跟不上代码变更 | 在 CLAUDE.md 中加入"代码变更必须同步文档"的规则 |

## 十二、总结

本方案的核心原则：

1. **按性质组织 + 版本年轮**：主目录按性质组织便于查找，`version-history.md` 提供版本演进视角
2. **单一信源**：同一信息只在一处维护，避免重复
3. **版本演进可追溯**：通过 `docs/reviews/` 和 `docs/version-history.md` 形成"年轮"
4. **待做事项集中管理**：`docs/backlog.md` 作为项目"卫生情况"总入口
5. **文档唯一性**：每个文档只放一个最合适的位置，不搞副本或符号链接
6. **文件名规范化**：统一使用英文命名
7. **轻量维护**：简化文档生命周期管理，降低维护成本
8. **入库流程标准化**：聊天记录入库有明确的评估、精简、命名、存放流程
