## 一、背景与目标

### 1.1 问题背景

项目当前存在 **59 个 markdown 文件**，分布在 **7+ 个目录**中，存在以下核心问题：

| 问题类型 | 具体表现 | 影响 |
|---------|---------|------|
| **分类混乱** | 开发手记、故障排查、技术决策、代码审查混放 | 难以定位所需文档 |
| **严重重叠** | Meal 系统 3 份文档、测试体系 6 份文档、幽灵文件夹 3 份文档存在大量重复 | 信息冗余、维护困难 |
| **版本失配** | 部分文档与当前代码不一致（如 README 项目结构过时） | 误导读者 |
| **缺少索引** | 无全局导航，新开发者难以快速定位 | 学习成本高 |
| **命名不一致** | 中英文混用（如 `chat-幽灵文件夹排查指南.md`） | 不专业、不便于检索 |

### 1.2 重构目标

1. **清晰的结构**：每种文档类型有明确的存放位置
2. **单一信源**：同一信息只在一处维护，避免重复
3. **易于维护**：简化文档生命周期管理，降低维护成本
4. **双向友好**：人类易于阅读导航，AI 易于理解上下文
5. **可溯源**：历史文档归档保留，便于回溯决策背景

### 3.2 关键决策理由

#### 决策 1：CHANGELOG.md 保留在根目录

**理由**：
- Keep a Changelog 规范明确要求 CHANGELOG.md 放在项目根目录
- GitHub 项目惯例：用户期望在根目录找到 CHANGELOG
- 无需在 docs 中创建副本，避免同步问题

#### 决策 2：`.trae/specs/` 保留原位

**理由**：
- `.trae/specs/` 是 Trae IDE 的 spec 工作流文件，位置由工具决定
- 移动可能影响工具功能
- 已实现的 spec 通过归档副本到 `docs/archive/specs/` 保留历史

#### 决策 3：创建 `docs/decisions/` 目录（ADR）

**理由**：
- ADR（Architecture Decision Records）是业界认可的最佳实践
- 对技术决策的溯源非常有价值
- 格式轻量，维护成本低

#### 决策 4：简化元数据标签

**理由**：
- 个人项目无需复杂的生命周期管理流程
- `last-reviewed` 可通过 git log 查询
- `scope` 可通过目录位置推断
- 仅保留 `status` 标签即可满足需求

#### 决策 5：使用 `docs/README.md` 作为索引

**理由**：
- GitHub 会自动显示目录下的 README.md
- 用户进入 docs 目录即可看到导航
- 符合 GitHub 项目惯例

## 四、文档分类标准

### 4.1 文档类型与存放位置

| 类型 | 存放位置 | 命名格式 | 用途 |
|------|---------|---------|------|
| **快速上手** | `docs/getting-started.md` | 固定名称 | 5 分钟内让新用户跑通系统 |
| **系统架构** | `docs/architecture.md` | 固定名称 | 描述系统整体架构、模块关系 |
| **CLI 参考** | `docs/cli-reference.md` | 固定名称 | 所有 CLI 命令的完整参考 |
| **配置参考** | `docs/config-reference.md` | 固定名称 | config.yaml 所有配置节说明 |
| **使用指南** | `docs/guides/` | `<功能>-guide.md` 或 `<功能>-system.md` | 功能使用指南 |
| **技术决策** | `docs/decisions/` | `NNNN-<简短描述>.md` | ADR 格式的决策记录 |
| **故障排查** | `docs/troubleshooting/` | `<问题描述>.md` | 已解决故障的排查记录 |
| **历史归档** | `docs/archive/` | 保持原名或重命名为英文 | 只读历史文档 |

### 4.2 状态标签规范

每个文档头部包含简化状态标签：

```markdown
<!-- status: active | archived | deprecated -->
```

- `active`：当前有效，需随代码更新（默认状态，可省略）
- `archived`：历史参考，不再主动维护
- `deprecated`：已被其他文档替代，保留仅供溯源

### 4.3 何时不创建文档

| 场景 | 替代方案 |
|------|---------|
| 代码注释能说明的问题 | 直接写在代码里 |
| API 变更 | 更新 `CHANGELOG.md` |
| 临时想法/TODO | 更新 `TODO.md` |
| AI 对话原始记录 | 不保存，仅保存提炼后的结论 |

## 八、长期维护机制

### 8.1 文档更新触发条件

| 代码变更类型 | 需更新的文档 |
|-------------|-------------|
| CLI 参数变更 | `docs/cli-reference.md` |
| config.yaml 结构变更 | `docs/config-reference.md` |
| 新增/删除模块 | `docs/architecture.md` |
| 新增功能 | 对应 `docs/guides/*.md` |
| Bug 修复 | `docs/troubleshooting/` 中的排障记录 |
| 重大技术决策 | `docs/decisions/NNNN-*.md` |

### 8.2 审查周期

- **每次发版前**：检查所有 `active` 文档与代码的一致性
- **每月**：通过 `git log --since="1 month ago" --name-only` 快速识别可能过时的文档

### 8.3 AI 协作规范

在 CLAUDE.md 中加入以下规则：

```markdown
### 文档维护规则

- 创建新功能时，同步创建 `docs/guides/<feature>-guide.md`
- 修复疑难 bug 时，创建 `docs/troubleshooting/<bug-name>.md`
- 做出重大技术决策时，创建 `docs/decisions/NNNN-*.md`
- 代码变更必须同步更新相关文档
```

## 十、风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| 迁移过程中链接失效 | 迁移前扫描所有文档中的内部链接，迁移后统一更新 |
| 合并文档时信息丢失 | 合并前先备份，保留所有原文档至归档目录 |
| 团队成员不熟悉新结构 | 在 CLAUDE.md 和 README 中明确文档规范 |
| 文档更新跟不上代码变更 | 在 CLAUDE.md 中加入"代码变更必须同步文档"的规则 |

## 十一、总结

本方案的核心原则：

1. **单一职责**：每种文档类型有明确的存放位置和命名规范
2. **单一信源**：同一信息只在一处维护，避免重复
3. **版本同步**：文档必须与代码版本保持一致
4. **易于查找**：通过 `docs/README.md` 实现一键定位
5. **轻量维护**：不创建不必要的文档，简化生命周期管理
6. **归档而非删除**：保留历史参考价值，但不影响日常使用
