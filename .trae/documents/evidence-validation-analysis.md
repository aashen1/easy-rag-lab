* 发现LLM生成答案时经常出现"10倍单位换算错误"（元→亿元）

**第二阶段（v0.1.10）**：扩展验证范围

* 发现引用太短或不存在于文档中

* 添加多级fallback：segment → sibling segment → document\_fuzzy

**第三阶段（v0.1.11）**：精细化调优

* 发现专有名词检测假阳性太多（"这些技术"被误判为专有名词）

* 添加 `is_genuine_proper_noun()` 过滤推理性过渡短语

* 添加时间表达式跳过（避免"3月"被当作数值检查）

### 1.3 当前状态

证据验证现在是一个**多层防御体系**：

```
LLM生成答案
    ↓
validate_evidence()          ← 验证引用是否存在于文档
    ↓
validate_numerical_accuracy() ← 检测10倍单位换算错误
    ↓
validate_answer_consistency() ← 检测正负号矛盾
    ↓
validate_answer_evidence_consistency() ← 检查答案中的数值/专有名词是否在证据中
    ↓
filter_adversarial_issues()  ← 对抗性问题特殊处理
    ↓
supplement_evidence_for_uncovered_numbers() ← 自动补充缺失数值的证据
```

## 二、这个做法是否主流？

### 2.1 主流做法是什么？

**主流RAG评测数据集生成工具**（如RAGAS、ARES、DeepEval等）的做法：

| 工具       | 证据验证方式          |
| -------- | --------------- |
| RAGAS    | 不验证，依赖人工审核      |
| ARES     | 不验证，使用LLM评估答案质量 |
| DeepEval | 不验证，提供答案正确性评估指标 |
| TruLens  | 不验证，提供反馈函数评估    |

**主流做法的核心思路**：

1. LLM生成问题和答案
2. 人工审核确保质量
3. 或者用另一个LLM来评估答案质量

### 2.2 我们的做法是什么？

我们的做法是**在生成阶段就做严格验证**：

* 验证引用是否真实存在于文档

* 验证答案中的数值是否在证据中出现

* 验证专有名词是否在证据中出现

* 不通过验证的问题会被拒绝并重新生成

### 2.3 结论：这是"补丁"而非"常规做法"

**为什么说是补丁？**

1. **问题驱动的开发**：每发现一个问题就加一个验证，不是一开始就设计好的
2. **与项目整体风格不契合**：项目其他地方都是"生成→评估"模式，这里是"生成→验证→拒绝→重试"
3. **增加了复杂度**：validators.py 有1200行代码，比很多核心模块还长
4. **不是行业标准**：没有其他RAG评测工具这样做

**但也有合理之处**：

* 金融研报对数值准确性要求高

* 人工审核成本高，需要在生成阶段就过滤掉明显错误

* 减少后续人工精修的工作量

## 三、当前证据验证有什么问题？

### 3.1 问题一：过于严格（主要问题）

**现象**：从刚才生成的20题golden test可以看到，有9道题存在 `answer_evidence_issues`

**原因分析**：

1. **数值检查过于死板**

   * LLM在答案中可能会做一些计算或推理，比如"增长约10%"

   * 但这个"10%"可能是LLM根据原文数据计算出来的，原文不一定有这个数字

   * 系统会报错：`数值 '10%' 未在证据中找到`

2. **专有名词检测不够智能**

   * 比如"显示非利息业务"被标记为专有名词

   * 但这其实是LLM的推理性语言，不是真正的专有名词

   * 虽然加了 `is_genuine_proper_noun()` 过滤，但还是有很多漏网之鱼

3. **对推理型问题不友好**

   * 推理型问题的答案本身就包含LLM的推理

   * 强制要求答案中的所有信息都在证据中出现，会限制答案的深度

### 3.2 问题二：验证逻辑分散

**现象**：验证逻辑分散在多个函数中，难以理解和维护

**具体表现**：

* `validate_evidence()` 在 validators.py

* `validate_numerical_accuracy()` 在 validators.py

* `validate_answer_consistency()` 在 validators.py

* `validate_answer_evidence_consistency()` 在 validators.py

* `_post_process_question()` 在 generator.py 调用这些验证

* `filter_adversarial_issues()` 在 validators.py

* `supplement_evidence_for_uncovered_numbers()` 在 validators.py

### 3.3 问题三：验证阈值缺乏灵活性

**现象**：所有问题类型使用相同的验证标准

**问题**：

* 单知识点查询：应该严格，答案中的信息都应该在证据中

* 推理型问题：应该宽松，允许LLM做一些推理

* 对比分析问题：应该中等，允许跨段落整合信息

**当前做法**：

* 对抗性问题有特殊处理（`filter_adversarial_issues`）

* 但其他类型的问题都用相同标准

### 3.4 问题四：重试机制效率低

**现象**：验证失败后重新生成，但可能生成类似的问题

**问题**：

* 最多重试3次，每次都要调用LLM

* 如果LLM倾向生成某种类型的问题，重试可能生成类似的问题

* 浪费API调用

## 四、改进建议

### 4.1 短期改进（不改变架构）

1. **放宽数值检查**：

   * 对于推理型、对比型问题，跳过数值检查

   * 只对单知识点查询做严格数值检查

2. **改进专有名词检测**：

   * 扩充 `is_genuine_proper_noun()` 的过滤词表

   * 或者直接禁用专有名词检查（因为假阳性太多）

3. **按问题类型调整验证严格度**：

   ```python
   VALIDATION_STRICTNESS = {
       "single_fact": "strict",      # 严格
       "adversarial": "strict",      # 严格
       "multi_fact": "moderate",     # 中等
       "comparative": "moderate",    # 中等
       "reasoning": "lenient",       # 宽松
       "missing": "none",            # 不验证
       "irrelevant": "none",         # 不验证
   }
   ```

### 4.2 中期改进（重构验证逻辑）

1. **统一验证入口**：

   ```python
   def validate_question(
       qa: dict,
       doc_content: str,
       strictness: str = "moderate",
   ) -> tuple[bool, list[str]]:
       """统一的问题验证入口"""
       pass
   ```

2. **分离"硬错误"和"软警告"**：

   * 硬错误：引用不存在、数值完全错误 → 拒绝问题

   * 软警告：数值近似、专有名词未找到 → 记录但不拒绝

### 4.3 长期改进（回归主流做法）

1. **减少生成阶段验证**：

   * 只保留最基本的验证（引用是否存在）

   * 其他验证移到后处理阶段

2. **增加人工审核工具**：

   * 提供更友好的审核界面

   * 让人工来决定哪些问题需要修改

3. **或者用LLM评估代替规则验证**：

   * 用另一个LLM来评估答案质量

   * 比规则验证更灵活
