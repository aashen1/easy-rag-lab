## 📊 项目链路总览

这是一个**金融研报RAG问答系统**，包含两条核心链路：**索引构建（Build Index）** 和 **问答检索（Query）**

---

### 链路一：索引构建（Index Building）

**入口**: `python main.py --build-index`

#### Step 1: PDF 解析
- **模块**: [src/parser.py](file:///b:/project/ash-easy-rag/src/parser.py)
- **库**: `pymupdf4llm`
- **流程**: `data/raw/*.pdf` → 解析为 Markdown 格式 → 保存至 `data/parsed/`
- **特点**: 
  - 已解析的PDF会跳过（避免重复），除非使用 `--force-parse`
  - 支持按 `--sample-count/pages/ratio` 抽样PDF

#### Step 2: 文档分块
- **模块**: [src/chunker.py](file:///b:/project/ash-easy-rag/src/chunker.py)
- **策略**: **固定长度分块（Fixed-size Chunk）**
- **配置**（[config.yaml](file:///b:/project/ash-easy-rag/config.yaml#L36-L40)）：
  - `chunk_size: 512` 字符
  - `chunk_overlap: 0` 无重叠
- **输出**: 保存至 `data/chunks/`，JSONL格式

#### Step 3: Embedding 向量化
- **模块**: [src/embedder.py](file:///b:/project/ash-easy-rag/src/embedder.py)
- **模型**: `BAAI/bge-large-zh-v1.5`（本地模型）
- **设备**: `cuda`
- **批处理大小**: 32

#### Step 4: 向量存储
- **模块**: [src/indexer.py](file:///b:/project/ash-easy-rag/src/indexer.py)
- **方案**: **Qdrant 向量数据库**（持久化存储）
- **距离度量**: `Cosine`（余弦相似度）
- **持久化路径**: `data/vector_store/`

---

### 链路二：问答检索（Query & Answer）

**入口**: `python main.py --query "你的问题"`

#### Step 1: 检索相关文档（Retrieval）
- **模块**: [src/retriever.py](file:///b:/project/ash-easy-rag/src/retriever.py)
- **流程**: 
  1. 将查询问题用 Embedding 模型向量化
  2. 在 Qdrant 中执行向量相似度检索
  3. 返回 Top-K 个相关 chunk（默认 `top_k: 5`）
- **输出**: 返回 chunks 文本 + 相似度分数 + 来源元数据

#### Step 2: LLM 生成回答（Generation）
- **模块**: [src/generator.py](file:///b:/project/ash-easy-rag/src/generator.py)
- **SDK**: Anthropic SDK
- **基座模型**: LongCat 在线 API（兼容 Anthropic 接口）
- **配置**: 通过 `.env` 配置 API Key 和 Base URL
- **Prompt**: 
  - 系统提示词定义金融研报分析助手的角色
  - 将所有检索到的 contexts 作为参考资料拼接
  - 附加用户问题，要求基于资料回答
- **参数**: `temperature: 0.0`（确定性输出），`max_tokens: 1024`

## 📦 Meals 功能设计调研报告

### 一、核心概念

**Meal（数据集配置）** 是对一组 PDF 文档及其对应的向量索引的完整封装。它将**原始 PDF 文件集合 + 配置快照 + 向量索引**绑定在一起，形成一个可独立管理、可复用的数据集单元。

---

### 二、核心数据结构

#### 1. [MealFile](file:///b:/project/ash-easy-rag/src/meal.py#L25-L29) - 单个 PDF 文件元数据
```python
path: str          # PDF 相对路径
sha256: str        # 文件内容哈希（用于完整性校验）
size_bytes: int    # 文件大小
```

#### 2. [MealConfig](file:///b:/project/ash-easy-rag/src/meal.py#L32-L73) - Meal 完整配置
| 字段 | 说明 |
|------|------|
| `data_id` | 基于所有 PDF SHA256 计算的哈希，唯一标识数据集内容 |
| `name` | Meal 名称 |
| `created_at` | 创建时间 |
| `sampling_config` | 抽样配置（count/pages/ratio + seed） |
| `collection_name` | Qdrant 向量集合名称 |
| `pdf_files` | PDF 文件列表（MealFile[]） |
| `config_snapshot` | 关键配置快照（parser/chunker/embedding/retrieval） |
| `config_hashes` | 各阶段配置的哈希值 |
| `stats` | 统计信息（PDF数、页数、块数、缓存命中情况） |

#### 3. [MealStatus](file:///b:/project/ash-easy-rag/src/meal.py#L18-L22) - 状态枚举
```python
AVAILABLE      # ✅ 可用 - 所有 PDF 文件存在且未改变
FILES_MISSING  # ⚠️ 缺失 - 部分 PDF 文件丢失
FILES_CHANGED  # ❌ 改变 - 部分 PDF 文件内容改变（SHA256不匹配）
MIXED          # ❌ 混合 - 同时存在缺失和改变的文件
```

---

### 三、核心身份标识机制

#### `data_id` - 数据集内容指纹
```python
data_id = SHA256(排序后的PDF文件SHA256列表)
```
- **相同 PDF 集合 → 相同 data_id**
- 不同 meal 可以有相同的 data_id（即共享相同的数据来源）

#### `collection_name` - 向量索引名称
```python
index_key = SHA256(data_id + parser_hash + chunker_hash + embedding_hash)
collection_name = "m_" + index_key[:12]
```
- 只有当 **PDF 集合 + 处理配置完全一致** 时，才会共享同一个向量集合
- 这意味着不同的分块策略或 Embedding 模型会生成不同的 collection

#### 配置哈希计算
```python
parser_hash    = SHA256(算法类型)[:8]
chunker_hash   = SHA256(chunk_size + overlap + encoding)[:8]
embedding_hash = SHA256(model_name)[:8]
```

### 四、核心功能操作

#### 1. 创建 Meal - `create_meal()`
**流程**：
1. 生成 Meal 名称（时间戳或自定义）
2. 按抽样配置（count/pages/ratio）选择 PDF 文件
3. 计算每个 PDF 的 SHA256 和文件大小
4. 计算 `data_id` → `index_key` → `collection_name`
5. **检查 Artifact 缓存**（避免重复解析/分块）
6. 解析 PDF → 分块 → 构建向量索引
7. 保存 `manifest.json` 到 `data/meals/{name}/`
8. 更新 Artifact 缓存的 manifest

**缓存机制**（[ArtifactCache](file:///b:/project/ash-easy-rag/src/meal.py#L139-L191)）：
```
data/artifacts/
├── {data_id[:12]}/
│   ├── manifest.json          # 缓存元数据
│   ├── parsed/                # 解析后的 Markdown 文件
│   │   └── *.md
│   └── chunks_{chunker_hash}/ # 分块结果（带配置哈希区分）
│       └── *.jsonl
```
- 相同 `data_id` 共享相同的 `parsed/` 目录
- 相同 `data_id` + 相同 `chunker_hash` 共享相同的 `chunks/` 目录

---

#### 2. 状态检查 - `check_meal_status()`
- 遍历 meal 中的所有 PDF 文件
- 检查文件是否存在
- 检查 SHA256 是否与创建时一致
- 返回状态枚举 + 问题列表

---

#### 3. 删除 Meal - `delete_meal()`
- 检查 Qdrant collection 是否被其他 meal 共享（通过 `_is_collection_shared()`）
- 如果未共享，删除向量集合
- 删除 `data/meals/{name}/` 目录
- **注意**: 不会删除 Artifact 缓存（避免影响其他同 data_id 的 meal）

---

#### 4. 重命名 Meal - `rename_meal()`
- 仅修改目录名称和 manifest 中的 `name` 字段
- **不改变** `data_id`、`collection_name` 等任何内容标识

---

#### 5. 复制 Meal - `copy_meal()`
- 浅拷贝（shallow copy）：复制 manifest，不复制数据
- 新 meal 与原 meal **共享相同的** `data_id` 和 `collection_name`
- 节省存储空间，适合用不同名称引用同一数据集

---

#### 6. 修复 Meal - `repair_meal()`
**场景**：原始 PDF 文件被删除或内容改变

**两种方式**：
1. **创建新 meal**（推荐）：保留原 meal，新 meal 有新的 `data_id` 和 `collection_name`
2. **原地修复**：更新当前 meal，会改变 `data_id`

**流程**：
1. 输入替换文件路径映射（旧路径 → 新路径）
2. 跳过无法替换的文件
3. 重新计算 `data_id` 和 `collection_name`
4. 重新解析/分块/构建索引
5. 保存更新后的 manifest

#### 1. 事实性问题（Factual）- `easy`

**核心思想**：从单个 chunk 生成可以用该文本直接回答的问题

**Chunk 选择逻辑** ([_select_chunks_for_factual](file:///b:/project/ash-easy-rag/src/test_generator.py#L226-L239))：
```
1. 将所有文档的 chunks 平铺
2. 随机采样 num_questions 个 chunks
3. 每个 chunk 生成一个问题
```

**Prompt 设计** ([FACTUAL_PROMPT](file:///b:/project/ash-easy-rag/src/test_generator.py#L13-L27))：
- 要求问题必须能用提供的文本**完全回答**
- 问题要具体、明确
- 难度标记为 `"easy"`

---

#### 2. 边界问题（Boundary）- `medium`

**核心思想**：测试信息被 chunk 边界切断时系统的检索和回答能力

**Chunk 选择逻辑** ([_select_chunks_for_boundary](file:///b:/project/ash-easy-rag/src/test_generator.py#L241-L256))：
```
1. 对每个源文件的 chunks 按 chunk_index 排序
2. 找到相邻的 chunk 对 (i, i+1)
3. 随机采样 num_questions 对
```

**Prompt 设计** ([BOUNDARY_PROMPT](file:///b:/project/ash-easy-rag/src/test_generator.py#L29-L44))：
- 提供两个相邻片段
- 要求生成需要**同时参考两个片段**才能完整回答的问题
- 难度标记为 `"medium"`

**价值**：这是 RAG 系统中非常典型的痛点测试，检验系统在信息被分割时的表现。

---

#### 3. 多跳问题（Multi-Hop）- `hard`

**核心思想**：需要综合多个非相邻片段的信息才能回答的复杂问题

**Chunk 选择逻辑** ([_select_chunks_for_multi_hop](file:///b:/project/ash-easy-rag/src/test_generator.py#L258-L272))：
```
1. 对每个源文件
2. 选择不相邻的 chunk 对 (i, j)，其中 j >= i+2 且 j <= i+4
3. 确保跳过了中间的 chunk(s)
4. 随机采样 num_questions 组
```

**Prompt 设计** ([MULTI_HOP_PROMPT](file:///b:/project/ash-easy-rag/src/test_generator.py#L46-L59))：
- 提供多个非相邻片段
- 要求问题**不能仅凭单个片段回答**
- 需要对比、综合或推理
- 难度标记为 `"hard"`

### 三、生成流程详解

[generate_test_set()](file:///b:/project/ash-easy-rag/src/test_generator.py#L72-L159) 完整流程：

```
1. 加载 meal 配置
   └─ 加载 meal_config（包含 PDF 列表、抽样配置等）

2. 加载文档块 (_load_meal_chunks)
   └─ 从 data/chunks/*.jsonl 加载
   └─ 只保留 meal 中 PDF 对应的 chunks（通过 source_filter）

3. 按源文件分组 (_group_chunks_by_source)
   └─ 按 metadata.source 分组
   └─ 每组内按 chunk_index 排序

4. 选择 chunks (_select_chunks)
   └─ 根据策略选择相应 chunks

5. LLM 生成问答 (_generate_question_with_llm)
   └─ 使用 Generator 调用 LLM
   └─ temperature=0.7（允许一定变化性）
   └─ max_tokens=512
   └─ 失败重试（最多 max_retries 次）

6. 解析 LLM 响应 (_parse_llm_response)
   └─ 提取 JSON 格式的 {question, answer, difficulty}
   └─ 容忍 markdown 代码块包裹

7. 组装测试集
   └─ 添加 id、source_chunks、source_files、category

8. 保存测试集 (_save_test_set)
   └─ 保存到 data/meals/{meal_name}/test_sets/auto_{strategy}.json
```

### 五、评测执行逻辑

[run_evaluation()](file:///b:/project/ash-easy-rag/eval/run_eval.py#L20-L134) 流程：

```
1. 加载测试集（支持列表格式或字典格式）
2. 可选：采样部分测试用例快速评估
3. 对每个测试用例：
   ├─ pipeline.query(question)  →  检索 + 生成回答
   ├─ 计算检索指标：
   │  ├─ Hit Rate：检索到的来源与期望来源的匹配比例
   │  ├─ MRR：第一个匹配结果的位置的倒数
   │  └─ NDCG：归一化折损累计增益
   └─ 记录回答内容、耗时、来源
4. 计算平均指标
5. 输出报告到 data/eval/baseline_report.json 或 meal 目录
```

**检索指标详解**：

| 指标 | 公式 | 含义 |
|------|------|------|
| **Hit Rate** | `|retrieved ∩ expected| / |expected|` | 召回率，检索到多少期望来源 |
| **MRR** | `1/(first_match_position)` | 平均倒数排名，第一个正确答案的位置 |
| **NDCG** | `DCG / IDCG` | 归一化折扣累计增益，考虑排名权重 |

### 七、设计亮点与局限

#### ✅ 亮点

1. **基于真实文档生成**：问题直接来源于真实研报内容，而非人工编写
2. **难度梯度设计**：三种策略覆盖 easy/medium/hard 三个难度级别
3. **Golden Answer 自动生成**：LLM 同时生成问题和期望答案，可作为评测基准
4. **来源追踪**：每个问题都记录了来源文件和 chunk，支持精确的检索质量评估
5. **与 meal 深度集成**：测试集绑定到特定 meal，确保数据一致性
6. **可复现性**：通过 seed 参数保证生成的可复现性

#### ⚠️ 局限

1. **仅实现检索质量指标**：Hit Rate、MRR、NDCG 已实现
2. **生成质量指标缺失**：Faithfulness、Answer Relevancy 标记为"待实现"（config.yaml 中有定义但未实现）
3. **无 RAGAS 集成**：虽然 config 中提到了 RAGAS，但实际未使用 RAGAS 库
4. **LLM 生成答案的质量风险**：golden answer 完全依赖 LLM 生成，没有人工校验
5. **边界策略的局限性**：只考虑相邻 chunk，没有考虑跨文档的边界情况

## 三、需要优化的地方（按优先级排序）

### 🔴 P0：紧急（直接影响系统可用性）

#### 1. 生成质量评测完全缺失

**现状**：
- `config.yaml` 中定义了 `faithfulness` 和 `answer_relevancy`
- `eval/metrics.py` 只有检索指标（Hit Rate、MRR、NDCG）
- 没有任何生成质量计算逻辑

**为什么紧急**：
- RAG系统的核心价值在于"生成回答的质量"
- 仅有检索指标无法评估系统是否给出了正确、相关的答案
- 无法量化 baseline 的完整性能

**建议方案**：
- 方案A（轻量）：实现基于规则的评估
  - Faithfulness：检查回答中引用的事实是否都能在检索到的contexts中找到
  - Answer Relevancy：计算回答与问题的语义相似度（可用Embedding）
- 方案B（推荐）：集成 RAGAS 库
  - 使用 LLM-as-Judge 进行评估
  - 需要额外调用 LLM，但评估更准确

---

#### 2. 当前分块策略过于简单

**现状**：
```yaml
chunker:
  chunk_size: 512
  chunk_overlap: 0  # 无重叠
```

**问题**：
- `overlap=0` 意味着相邻 chunk 之间完全没有重叠
- 关键信息可能恰好被切割在两个 chunk 之间（这正是 boundary 测试要暴露的问题）
- 512 字符可能太短（中文字符约150-170个），丢失上下文

**建议优先级**：
1. 首先设置 `chunk_overlap: 50-100`（低成本高收益）
2. 后续考虑语义分块（如基于段落/标题边界）

---

### 🟠 P1：重要（显著提升系统性能）

#### 3. 纯向量检索的局限性

**现状**：仅使用余弦相似度进行向量检索

**问题**：
- 向量检索擅长语义匹配，但不擅长精确匹配（如人名、数字、专有名词）
- 金融研报中包含大量具体数据（营收、利润、年份等），纯向量检索容易漏掉

**建议方案**：
- 引入 **混合检索（BM25 + 向量）**
  - BM25 擅长关键词精确匹配
  - 向量检索擅长语义理解
  - 两者加权融合（如 alpha=0.5）
- 这是项目 Backlog 中"高优先级"的第一项

---

#### 4. 缺少重排（Reranker）阶段

**现状**：检索直接返回 Top-K 向量相似度结果，无二次排序

**问题**：
- 向量相似度 ≠ 实际相关性
- 有些文档向量相似但内容不相关，会污染生成阶段

**建议方案**：
- 在检索后、生成前加入 Reranker
- 推荐模型：`BAAI/bge-reranker-large` 或 Cross-Encoder 模型
- 流程：向量检索 Top-50 → Reranker 重排 → 取 Top-5 给 LLM

---

#### 5. 查询过于朴素

**现状**：用户问题直接用于向量检索，无任何处理

**问题**：
- 用户问题可能表述不清、过于宽泛或包含歧义
- 直接检索效果受限于问题本身的表述质量

**建议方案（按复杂度递增）**：
1. **查询改写**：用 LLM 将问题改写为更适合检索的形式
2. **Multi-Query**：生成多个变体问题，分别检索后合并结果
3. **HyDE**：先生成一个假设性答案，用答案去检索相似文档

---

### 🟡 P2：中等（改善用户体验或系统健壮性）

#### 6. 评测流程自动化不足

**现状**：
- 需要手动执行 `python main.py --generate-test-set` 和 `python eval/run_eval.py`

**现状**：LLM 生成的问答对直接使用，无质量过滤

**问题**：

- 低质量测试集会污染评测结果

**建议**：

  - 问题和答案长度阈值
