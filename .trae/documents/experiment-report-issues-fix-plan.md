## 根因排查计划

### 问题 1：耗时数据不一致

**排查步骤**：
1. 搜索 `profile_report.md` 生成逻辑
2. 搜索 `experiment_report.md` 中 `total_time_seconds` 的来源
3. 确认两者统计口径差异（是否包含 profiling 开销、测试集生成时间等）

**预期根因**：
- profile_report 统计的是整个 pipeline 耗时（包含 S1-S8 所有阶段）
- experiment_report 的 total_time 可能只统计 RAG 问答阶段

---

### 问题 2：测试集 ground truth 错误 (q007)

**排查步骤**：
1. 读取测试集生成逻辑 `TestSetGenerator`
2. 检查表格数据解析逻辑
3. 确认 EPS 字段的提取位置

**预期根因**：
- 表格数据格式为 `0700.HK|腾讯控股|买入|489.20|44642|24.75|26.70|28.94|17.8|16.5|15.2|105.53`
- 字段解析时可能将 `105.53`（某列）误认为是 2025 年 EPS

---

### 问题 3：检索失败未正确标记 (q004)

**排查步骤**：
1. 检索 q004 的 expected_sources 对应文档是否存在于 meal 中
2. 检查 embedding 是否正确生成
3. 确认检索评估逻辑中 hit_rate=0 的处理方式

**预期根因**：
- expected_sources 文档可能不在 5000 页样本中
- 或文档存在但检索语义匹配失败

---

### 问题 4：配置与实际执行不一致

**排查步骤**：
1. 搜索配置合并逻辑
2. 检查 `config_snapshot.yaml` vs `merged` 配置的差异来源
3. 确认 `evaluation.backends` 的实际使用逻辑

**预期根因**：
- 配置存在多层覆盖（experiment config > system config > default）
- `ragas.enabled: false` 在某层被设置

---

### 问题 5：指标缺失

**排查步骤**：
1. 搜索 `false_positive_rate` 计算逻辑
2. 搜索 `retrieval_diversity` 计算逻辑
3. 确认 `irrelevant_questions_count` 的统计逻辑

**预期根因**：
- 部分指标可能尚未实现
- 或计算条件不满足（如 irrelevant 问题数量不足）

---

### 问题 6：测试集分布偏差

**排查步骤**：
1. 检查 `type_distribution` 配置是否生效
2. 确认问题类型分配逻辑
3. 检查 hard 难度问题的生成条件

**预期根因**：
- 随机采样导致分布偏差
- hard 难度可能需要特定条件触发

---

### 问题 7：检索结果冗余

**排查步骤**：
1. 检查 Top-K 检索逻辑
2. 确认是否有文档级去重
3. 检查 `sources` 字段的生成逻辑

**预期根因**：
- 检索返回的是 chunk 级别结果
- 同一文档的多个 chunk 被返回

---

### 问题 8：报告格式问题

**排查步骤**：
1. 搜索 LLM 报告生成 prompt
2. 检查配置输出逻辑
3. 确认标题重复的原因

**预期根因**：
- LLM 报告 prompt 可能包含标题模板
- 配置输出逻辑未做去重

---

## 修复计划

### 阶段 1：数据层修复（P0）

1. **修复耗时统计一致性**
   - 统一 profile_report 和 experiment_report 的时间统计口径
   - 或在报告中明确说明各时间含义

2. **修复测试集 ground truth**
   - 修复表格数据解析逻辑
   - 添加字段验证机制

3. **修复检索失败标记**
   - 检查 expected_sources 文档是否存在
   - 完善检索评估逻辑

### 阶段 2：逻辑层修复（P1）

4. **统一配置管理**
   - 明确配置优先级
   - 添加配置一致性检查

5. **完善指标计算**
   - 实现 FPR 计算
   - 实现 retrieval_diversity 计算
   - 修复 irrelevant_questions_count 统计

6. **优化测试集生成**
   - 添加分布校验
   - 增加 hard 难度问题生成

7. **优化检索去重**
   - 在 Top-K 后添加文档级去重
   - 或在 sources 输出时去重

### 阶段 3：展示层修复（P2）

8. **修复报告格式**
   - 去除标题重复
   - 优化配置输出（使用引用代替重复）

9. **添加说明**
   - CPU 使用率添加多核说明
   - 修复 chunk_retrieval 缺失字段

## 验证方案

### 验证命令

```bash
pixi run exp quick_verify_metrics
```

### 验证流程

```
修复 → 运行验证 → 检查结果 → 
  ├── 通过 → 完成
  └── 失败 → 分析问题 → 继续修复 → 重新验证
```

### 验证检查项

1. **耗时一致性**：profile_report 与 experiment_report 时间匹配
2. **Ground Truth 正确性**：数值类问题答案准确
3. **检索标记正确**：hit_rate=0 的问题正确处理
4. **指标完整性**：FPR、diversity 等指标有值
5. **报告格式**：无重复标题、无重复配置输出

### 迭代策略

- 每轮修复后运行 `pixi run exp quick_verify_metrics`
- 分析验证报告，识别剩余问题
- 持续迭代直到所有检查项通过
